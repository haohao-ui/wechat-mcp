# 生产落地执行方案：大脑配置界面、对话闭环与应用版本更新

日期：2026-11-10

状态：方案已落盘，尚未实施。本文不是项目验收报告。

## 1. 目标与范围

以现有可工作的单测、Rust 核心、Swift 手/眼和对话记录为基础，按以下顺序推进：

**配置化大脑 → 接通对话记录 → 稳定手/眼执行 → 应用整体更新 → 专用机试运行。**

用户已明确的要求：

- 大脑的角色定义不能写死在代码中。
- 欢迎、等待、无法回答、转人工等通用回复内容不能写死在代码中。
- 大脑配置必须支持在助手界面中管理。
- 增加应用自身的版本更新能力；“应用更新”不是指角色配置生效。
- 本阶段先形成方案，不实施源码修改、部署或发布。

最终用户可以在界面创建角色、维护知识和话术、选择大脑、测试并启用配置，查看可追溯的对话与执行结果，人工接管会话，以及检查、下载和安装应用更新。

首期运行形态是专用 Mac、单执行节点单微信账号、限定授权联系人及人工接管。扩容采用独立执行节点，不通过多个 Agent 并发抢占同一桌面。

## 3. 模块职责

| 模块 | 职责 | 输出与约束 |
|---|---|---|
| 眼 | 观察会话、消息、附件，判断内容是否稳定 | 带账号、时间、来源及不确定性的观察；不决定业务回复 |
| 对话记录 | 保存观察、上下文、决策、动作结果 | 可追溯的对话与轮次；不把生成内容当作已发送事实 |
| 大脑 | 结合角色、规则、知识和历史作决策 | 回复、跳过、等待或转人工；不能扩大执行权限 |
| 手 | 核验目标，执行切换、输入、发送等操作 | 动作是否触发、核验结果、失败与未知状态；不编造回复 |
| 核心 | 调度、权限、幂等、限流和故障恢复 | 确定的状态流转 |
| 助手界面 | 配置、观察、接管与更新 | 用户可理解、可操作的状态 |

代码保留账号隔离、白名单、权限、幂等、超时、状态机与数据访问规则。角色身份、语气、业务范围、知识、回复策略和通用话术进入配置。

**系统能力约束不进入角色配置**（审核补充）。现有提示词中有两类内容，必须拆开：

- 角色与话术：身份、语气、字数限制、首次自我介绍、业务范围等，进入配置，可在界面编辑。
- 系统能力约束：与代码数据结构绑定的契约，例如 `unreadable` 每项必须点名并按 hint 说明、`files` 中 `voice_transcript` 是对方本轮语音的转写、`recent_context` 中的图片和文件只作背景、`image_count` 以本轮为准、不能仅凭文件名声称读过正文。这些留在代码中，由代码拼接在角色内容之后，界面不可删改，并有测试覆盖。否则用户编辑一次角色就可能破坏图片、语音、文件的处理。

客户消息作为外部数据，不得作为更改权限或读取其他客户记录的指令。

## 4. 大脑配置界面

在现有助手中新增独立“大脑”页面，复用现有配置和导航组件。MCP 页面继续负责连接、令牌、外部接口和连通性检查，避免两页维护同一字段。

| 区域 | 内容 |
|---|---|
| 角色列表 | 新增、编辑、复制、归档；显示账号绑定情况 |
| 角色定义 | 名称、身份、目标、语言、语气、回答范围 |
| 业务规则 | 可回答范围、必须转人工条件、信息不足处理方式 |
| 业务知识 | 手动编辑、导入文本或 Markdown、预览、启用和停用 |
| 通用话术 | 欢迎、等待、无法回答、转人工等模板 |
| 模型连接 | 内置或外部模式、模型、连接测试、超时策略；复用现有连接配置 |
| 模拟测试 | 输入消息，查看回复和决策；不能操作微信 |

首版知识采用可预览的文本和 Markdown，不提前引入复杂知识库服务。上下文超限必须提示，不能静默丢弃知识。设计阶段须写明超限策略（按什么顺序截断、保存/启用时如何提示、运行中如何记录），并有对应测试。（审核补充）

每个话术模板包含名称、正文、启用状态、触发条件、允许变量、预览和冷却/频率约束。代码输出如 `model_timeout`、`handoff_required` 的状态，配置决定是否发送以及发送内容。未配置兜底话术时进入待处理或人工接管，不自动发送固定业务文案。

P1 的硬编码文案盘点须包含 `src/brain/builtin.rs` 中 `unreadable_hints` 的各条客户可见提示（如“请对方重发一次”“这条语音没能转成文字，请对方打字再说一次”），它们属于话术而非系统约束。（审核补充）

### 4.1 存储与生效

建议增加独立角色存储，主配置保存账号与角色的绑定引用：

```text
state/
├─ brain-profiles/
│  └─ <profile-id>/
│     ├─ revisions/<revision-id>.json
│     └─ knowledge/
└─ brain-bindings.json
```

配置包含 schema 版本、角色 ID、修订版本、规则、模板和知识引用。凭据沿用独立凭据机制，角色导出不包含密钥。知识引用必须固定版本或内容摘要，不能让历史修订引用可变文件。

生效流程：编辑 → 保存草稿 → 校验 → 模拟测试 → 启用配置。

- 保存草稿不改变运行配置。
- 启用前完整校验；配置文件原子写入，失败保留旧版本。
- 新轮次使用新版本，在途轮次使用开始时的版本快照。
- 界面分别显示已保存版本和运行中版本，并显示加载失败原因。
- 使用修订比较检测并发编辑，禁止静默覆盖。
- 被账号使用的角色不能直接删除，可先解除绑定或归档。
- 回退通过重新启用历史修订完成，保留完整审计记录。
- 用户角色、话术和知识不随应用升级被默认资源覆盖。

**从现有版本升级的迁移**（审核补充，阻塞项）：“未配置角色不隐式采用固定人设”只适用于新安装。从现有版本升级时，迁移必须把当前内置提示词中的角色部分与 `unreadable_hints` 话术，生成为一个**显式的默认角色修订**，写入角色存储并绑定到现有账号，在界面中可见、可编辑。否则专用机升级后会停止回复。迁移需幂等，并有“升级前后同一输入得到同类回复”的测试。

**绑定粒度与唯一来源**（审核补充，阻塞项）：现状下私聊与群聊回复规则已不同（群聊 @ 发言人），业务上大概率需要不同角色。绑定模型至少在数据结构上支持“账号默认角色 + 按联系人/群覆盖”。设计须明确 `brain-bindings.json` 与 `config.json` 白名单的关系：联系人范围只有一个真实来源，绑定只引用、不复制联系人清单。

## 5. 内置与外部大脑的一致性

统一生成每轮大脑输入快照：账号与联系人范围、角色版本、规则、知识版本、话术策略、该联系人历史、当前消息及附件。

内置大脑直接使用快照。外部大脑取得同一快照，或取得带版本、受权限约束的配置引用。不得仅在界面保存角色，而外部大脑继续使用另一套写死人设。

| 决策 | 核心行为 |
|---|---|
| 回复 | 校验后交给手执行 |
| 跳过 | 结束轮次并保存原因 |
| 等待 | 按有上限的等待策略重新观察 |
| 转人工 | 暂停该会话自动回复，显示原因 |

优先兼容现有外部接口的 `send/skip/handoff` 语义。“等待”是内部状态还是新增外部动作，需要在契约设计阶段确定，不直接修改现有客户端协议。

转人工复用现有 `handoff.json` 标记与会话暂停（`admin-pause.json`、按会话暂停），统一语义与界面展示，不新建第三套暂停机制。（审核补充）

外部大脑模式下的模拟测试会调用真实外部服务。契约须增加可识别的模拟标记，外部大脑不得把模拟轮次当作真实客户轮次记录、计费或写入其侧的会话状态；该字段按兼容性说明先行设计。（审核补充）

配置版本、上下文等新增字段先形成兼容性说明及契约测试，再实施。涉及公共接口或数据库变更时，提交具体设计供 Tech Lead 确认后进入相关开发。

## 6. 对话记录与手/眼闭环

复用现有历史存储，每个轮次关联：

- 账号、联系人、输入消息和观察来源。
- 角色修订、知识修订、模型与必要的请求元数据。
- 大脑决策及生成回复。
- 发送幂等键、执行阶段、错误和最终状态。
- 人工接管及处理结果。

不记录密钥。默认运行日志不写消息正文，业务内容通过受账号权限约束的对话记录查看。逐帧记录（`frame-dump.enabled`）与诊断截图只用于排查：默认关闭，开启须有明确期限并在界面可见，P0 先关闭专用机上当前开启的逐帧记录。（审核补充）

“模型已生成”“发送已触发”“观察到己方回显”“送达未知”分别展示。回显不等于送达，OCR 记录不等于完整历史。

模拟路径与真实路径复用上下文组装和大脑决策逻辑，但禁止调用手、写入真实客户历史或消费真实轮次。

| 异常 | 必须行为 |
|---|---|
| 会话目标不唯一 | 停止操作，要求核对 |
| 消息或语音转写未稳定 | 等待，不提前回复 |
| 窗口遮挡或权限缺失 | 返回具体原因，释放执行资源 |
| 人工切换会话或输入 | 识别冲突，暂停当前自动操作 |
| helper 超时 | 结束等待并释放锁，根据副作用阶段记录结果 |
| 发送中进程中断 | 保留未知状态，不自动换幂等键重发 |
| 打开有未读的会话时微信把首条未读顶到最上方（下方留白） | 翻页找回衔接点，回到底部按“画面末尾一致”确认；已于 `adb0191` 修复，列入真机回归（审核补充） |
| 同时长语音像素相同、身份冲突 | 按本轮消息序列在当前画面定位，worker 按位置与自下而上的排位跟踪；已修复，列入真机回归（审核补充） |

手/眼已有功能以集成验证和必要修复为主，不扩大为通用桌面自动化重写。

## 7. 应用版本更新

首版采用界面检查更新、用户确认安装、完整版本包替换，不做后台静默安装。

### 7.1 界面与分发

更新页面显示当前版本、可用版本、发布时间、说明、兼容要求和进度。支持检查、下载、安装并重启、稍后安装以及失败恢复。

宿主 App、Rust 核心、Swift worker/helper、布局与默认资源由统一版本清单描述。组件报告各自版本，启动时核对兼容范围。复用 worker 位于 App 包外的设计，以整套版本激活，避免组件混用。

发布清单包含版本、架构、最低系统要求、摘要、签名、配置及数据库兼容范围。摘要发现损坏，签名验证来源。签名和安装路径应保持稳定，并在目标机验证更新后的隐私权限行为。

当前私有仓库安装需要 GitHub Token。不能将开发者仓库 Token 打包进客户端。开发更新功能前确定分发方式：公开签名产物，或独立授权下载服务。更新源不得接受任意地址或未经验证的执行内容。

**两种签名必须分开设计**（审核补充，阻塞项）：

- **发布者签名**：验证更新包来源与完整性。用发布方私钥（如 ed25519）签名版本清单及各组件摘要，客户端内置公钥校验。
- **本机代码签名**：维持 macOS 隐私权限。当前由每台专用机的本地自签名证书完成，权限绑定该签名。更新包无法预先带上目标机的本地签名。

推荐流程：下载 → 校验发布者签名与摘要 → 用目标机本地签名钥匙串**重新代码签名** → 替换 → 自检。未公证、无 Developer ID 的前提下（现有设计的非目标）也必须走此路径，否则更新后权限失效、bot 停摆。须在专用机实测更新前后录屏与辅助功能权限保持。

### 7.2 更新状态机

```text
检查 → 下载 → 验证 → 等待安全时点
→ 暂停新轮次 → 备份 → 替换组件
→ 启动自检 → 恢复运行
```

- 下载期间继续工作。
- 安装前停止接收新轮次，等待在途轮次完成或进入安全暂停状态。
- 等待超时提供延期或停止处理选项，不能直接强杀正在发送的任务。
- 备份数据库、附件、角色、知识及绑定配置，记录备份与更新事务。
- 独立更新进程负责宿主退出后的替换和重启；必须协调现有 supervisor，防止旧进程在替换期间自动拉起。
- 计划内的停止与重启（更新、部署）不计入 `RestartPolicy` 的崩溃次数。现有“部署后 core 撞上 1 小时 5 次上限未恢复”的问题须在 P4 之前修复，否则更新流程会自行停掉服务。（审核补充，阻塞项）
- 新版本先检查组件、配置、数据库和 worker 连接，再恢复自动回复。
- 更新过程分阶段持久记录，断电重启后能判断继续、恢复还是待人工处理。
- 下载中断、验签失败不得影响旧版本运行。

### 7.3 回退

- 未发生不兼容迁移：回退组件版本，并验证配置兼容性。
- 发生不兼容迁移：停止服务，按对应备份恢复，明确列出数据影响范围。
- 新版本已经产生业务记录后，不能静默恢复旧数据库造成数据丢失；必须保留新数据副本，给出可审核的恢复步骤。
- 备份不可用或自检失败时，保持自动处理暂停并给出原因，不循环尝试发送。

## 9. 测试与验收

不重复重建已工作的基础测试；新增测试集中于行为变化、兼容和故障边界。

### 配置与大脑

- 配置损坏、缺字段、旧配置迁移、并发编辑冲突。
- 新配置启用时，在途轮次继续使用原版本。
- 内置与外部大脑使用一致的角色和上下文。
- 未配置兜底时不产生默认业务回复。
- 模拟测试不发送、不消费真实轮次、不污染客户记录。
- 角色导出、日志和接口不泄露凭据或越权历史。

### 对话与执行

- 配置修订、输入、决策、发送状态能关联查询。
- 同键重试及发送中断重启后不重复触发。
- 超时、权限缺失、遮挡及人工干预后释放资源并显示原因。
- 真机覆盖相同文本连续到达、多会话、联系人重名/改名、语音转写、微信退出和换号。

### 应用更新

- 下载断网、磁盘不足、签名错误、缺组件时旧版本可继续使用。
- 更新进程与 supervisor 不竞争，组件不会混用版本。
- 配置、对话、附件升级前后完整。
- 组件回退及不兼容迁移恢复分别演练。
- 更新各阶段中断后均有确定恢复路径。

### 工程检查

运行对应 Rust、Swift 和协议测试；完整构建门禁、原生组件构建、安装测试应在最终候选版本执行。全量单测通过不替代真机验收，真机单次成功不替代连续运行。

试点记录处理耗时、超时次数、人工接管、未知发送、恢复耗时及异常原因。没有可靠平台证据的送达率、全量漏读率保持 unknown。

## 10. 实施与交付约束

- 不覆盖现有脏 worktree；开始每项任务前记录基线与文件边界。
- 先复用现有配置、历史、备份和 supervisor，避免另建同类系统。
- 公共接口与数据库变更先提交具体设计及兼容方案。
- 每阶段汇报主要文件、实际测试、失败、风险与未验证项。
- 开发任务完成后按项目要求使用 Orca Orchestration 报告；不得自行宣布整个项目验收通过。
- 本方案落盘不授权部署、发布、真实消息发送或破坏性数据恢复。
