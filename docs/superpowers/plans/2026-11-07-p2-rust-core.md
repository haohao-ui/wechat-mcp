# P2 Rust 核心（内置大脑）Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 `scripts/wechat_bot`（Python，约 4300 行，约 360 个测试）的行为原样搬进 Rust：
- 由 `wechat-mcp serve-core` 常驻运行，完成监听、调度、记账、内置大脑和发送；
- 数据文件和数据库表不变，Python 和 Rust 可以互相切换。

**Architecture:**
- 在 crate 里新增 `src/core/`（调度、一轮消息、发送、策略、worker 客户端、状态文件）和 `src/brain/`（内置大脑）。
- 历史库放在 `src/core/history/`，读写同一个 SQLite 文件，表结构不变。
- 入口：`wechat-mcp serve-core --config <path>`。
- **行为规格就是现有的 Python 代码和测试**：每个任务先把指定的 Python 测试逐条翻译成 Rust 测试（测试名保持一致，前面加模块前缀），看到它们失败，再实现，直到通过。

**Tech Stack:**
- Rust（tokio、rusqlite、serde）；
- 新增 `reqwest`（`default-features = false, features = ["json", "rustls-tls"]`），供内置大脑访问 HTTPS 模型接口；
- macOS 12 x86_64 交叉编译。

**Spec:** `docs/superpowers/specs/2026-11-07-rust-core-pluggable-brain-design.md`（第 2、3、5、6 节，第 8 节决定记录）

## Global Constraints

- **行为一致优先于"改进"**：Python 的做法看起来不合理时，先照搬，再在报告里列出来。不要擅自改变行为。
- 文件格式完全兼容：日志文件 `send-*.json`、`cursor.json`、`health.json`、`admin-pause.json`、`*binding.json`、历史库 `history/history.sqlite3`、网关 `test.sqlite3`。Rust 写出的文件，Python 必须能读，反过来也一样。
- 状态文件按私有方式写入（权限 0600，先写临时文件再原子替换），和 Python 的 `write_private` 一样。
- 不改 MCP 工具名、参数和返回结构，也不改数据库结构。新增的 MCP 工具留到 P4。
- **只在本机运行**：核心服务和微信在同一台机器上，不移植 ssh 传输（`transport.py` 的远程模式）。配置里的 `host` 只接受 `local`。
- 发送一律走 P1 的路径：`wechat_click input-text` → 核对标题 → `key return`。
- 时间、路径、随机数都要能注入，测试不能依赖真实时钟、真实屏幕或网络。
- 不部署到专用 Mac，不 push。真机部分（Task 10）由协调者执行。

### Task 10: 影子运行与切换（由协调者执行）

> Ruling（2026-11-07）：采用"录制回放"，不在线影子运行。
> - **录制**：Python 机器人已经加了 `frame-dump.enabled` 开关（提交 fd15504），每次截屏都会追加写入 `sessions/<id>/frames-YYYYMMDD.jsonl`。每行一条记录，字段为 `t`（秒）、`op`、`recipient`、`frame`。专用 Mac 已于 2026-11-07 打开这个开关。
> - **T10a 回放工具**（派给 worker）：`wechat-mcp replay --config <cfg> --session <recipient> --frames <frames jsonl…> --journals <Python 会话目录> --work <空目录>`。
>   - 在 `--work` 下面用一份全新的状态目录驱动 T6 的 `BotService`：
>     - 截屏：同一个 cycle 里每次截屏都返回当前这一帧；
>     - 时钟：等于这一帧的 `t`；
>     - 等待：立即返回；
>     - 大脑：按 `batch_key` 去 Python 日志里查当时的 `reply`，查不到就记为 `missing_reply`，并使用占位回复；
>     - 发送：`send_message` 一律返回 triggered，不真的发出。
>   - 第一帧只用来建立基线，不回复。
>   - 输出 JSON 报告，逐个对比 Rust 和 Python 的 `idempotency_key` 和最终 `status`，分为四类：两边一致、只有 Rust 有、只有 Python 有、状态不同。
>   - 不访问网络，不连接 worker，不读写线上状态目录。
> - **协调者**：定期从专用 Mac 拷贝录制文件和日志文件到本地私有目录，跑回放，分析差异，直到连续 3 天没有无法解释的差异。
- `serve-core --shadow`：照常看屏幕、照常判断，但**绝不点击会话、不发送、不写日志文件和游标**，只把每一轮的判断写进 `shadow.jsonl`。
- 影子模式同样需要截屏，会和 Python 争用 worker 的唯一连接。所以影子模式不去连 worker，而是读取 Python 那边每次截屏后落盘的画面（需要在 Python 里加一个只读的画面转储开关），或者离线回放 `history` 和日志文件。具体做法在开始做这个任务时定下，并写进本计划。
- 比对报告：Python 的实际结果和 Rust 的判断逐轮对照。连续 3 天没有无法解释的差异后，再按设计第 6 节 P3 切换。

## Review Focus
1. 新旧格式混用：Rust 读到 Python 早期写的日志文件和游标（比如旧版指纹、`before-format-recovery` 文件）时，处理方式要和 Python 一样，不能因为反序列化失败就崩溃。
2. 两个进程同时写同一个历史库：切换期间不允许发生。Task 8 的开关必须保证同一时间只有一方在运行（文件锁加 launchd 状态检查）。
3. 时钟和时区：`observed_at`、`updated_at` 的单位（Python 里有毫秒和秒两种）要逐字段照搬。
4. 收到 SIGTERM 时正在发送：要等这一轮发送完成、日志写完再退出。如果直接退出，下次启动就会遇到"结果不确定"的日志。
5. 中文、表情、组合字符：计算长度和比较时，Python 按码位计数，Rust 的 `chars()` 也按码位计数。不要用字节数，也不要用字形簇数。
