# 通讯录同步与助手界面改版设计

日期：2026-11-08　状态：用户已确认（2026-11-08，"按新设计开始"）
实测依据：`docs/observations/2026-11-06-wechat-4.1.15-actions.md` §8

## 1. 目的

用户原话："第一次启动如果我们做一次联系人初始化，这是不是就可以更新管理每个人信息。后有新增联系人就自动同步更新。这样每个人的对话记录也就是对应，查询更方便。"分类："同微信分类"。

要解决的问题：现在联系人是"聊过天才建档"，只认显示名；改名要人工 merge-contact；查不到没聊过的人；也分不清公众号、企业微信联系人和个人好友。

成功标准：
- 首次初始化后，本地联系人库与微信通讯录一致（数量与微信分组数量相同）；
- 每个联系人有稳定身份（微信号），改备注/昵称后聊天记录仍归在同一人名下；
- 新加好友、改备注在下一次同步后出现在库里，无需人工录入；
- 允许名单可以从联系人库里按分类勾选。

## 2. 不做（非目标）

- 不读微信数据库或任何加密数据（红线不变），只看屏幕；
- 不修改微信里的任何东西：不改备注、不打标签、不删好友、不点「发消息/语音聊天/视频聊天」；
- 不做自定义业务分类（用户选择"同微信分类"）；微信里的标签照原样读取；
- 不同步朋友圈、头像图片。

## 3. 分类（同微信）

| 分类 `category` | 来源 | 默认处理 |
|---|---|---|
| `official` 公众号、服务号 | 通讯录分组 | 只建档，永不自动回复，不可加入允许名单 |
| `work` 企业微信联系人 | 通讯录分组 | 建档；可手动加入允许名单 |
| `personal` 联系人 | 通讯录分组 | 建档；可加入允许名单 |
| `group` 群聊 | 通讯录"群聊"分组（若有）+ 机器人见过的群 | 建档；可加入允许名单 |

本账号目前没有"群聊"分组（群没保存到通讯录）；群聊靠会话里见到的群建档，与现在一致。

## 4. 身份与对应关系

- **主键：微信号**（资料卡 `微信号：…`）。每个账号内唯一；没设过微信号的人显示系统分配的 `wxid_…`，同样唯一。
- 聊天窗口标题显示的是"备注（有备注时）或昵称"，所以把**备注、昵称**都登记为该联系人的名字（`contact_names`，新来源 `addressbook`）。会话里看到标题 → 查名字表 → 找到联系人 → 消息挂到这个人名下。
- 重名（两个人显示名相同）：名字表里同名指向多个人时，不自动归属，标记"需人工确认"，在面板提示，和现在的合并建议一样处理。
- 已有聊天历史的联系人：初始化时按名字匹配到通讯录条目，匹配唯一就把微信号补到现有联系人上（不新建、不搬数据）；不唯一就列为待确认。
- 公众号、企业微信联系人的资料卡字段待实测（§8 未覆盖），拿不到微信号时以"分类 + 名字"为身份，并标记 `identity=weak`。

## 5. 数据（聊天历史库新增一次迁移）

新表 `contact_profiles`（一人一行，`contact_id` 关联现有 `contacts`）：

| 字段 | 说明 |
|---|---|
| `contact_id` | 主键，关联 contacts |
| `account_id` | 微信账号 |
| `wechat_id` | 微信号；同账号内唯一（可空，见 §4 弱身份） |
| `category` | official / work / personal / group |
| `nickname` | 昵称（资料卡大字） |
| `remark` | 备注，未设置为空 |
| `region` | 地区 |
| `source` | 来源（如"通过搜索手机号添加"） |
| `added_on` | 添加时间（YYYY-MM-DD） |
| `common_groups` | 共同群聊数 |
| `tags` | 标签（通讯录管理表格里的，JSON 数组） |
| `friend_permission` | 朋友权限 |
| `identity` | strong（有微信号）/ weak |
| `first_synced_at` / `last_synced_at` | 首次 / 最近一次同步时间（毫秒） |
| `removed_at` | 同步时在通讯录里找不到了（删好友）；不删档、不删聊天记录 |

`contact_names.source` 增加 `addressbook`。现有 `contacts.kind` 保持不变（private/group），分类放在 `contact_profiles.category`。

## 6. 同步流程（全在专用 Mac 本机，按 §8 实测的界面操作）

**首次初始化**（面板按钮「初始化通讯录」，或 `wechat-mcp control contacts-sync --full`）：
1. 暂停自动回复（与现在的暂停相同，结束后自动恢复）；
2. 切到通讯录（导航栏 x≈30, y≈169），列表滚到顶；
3. 读三个分组标题和数量；
4. ~~打开「通讯录管理」读表格~~ **不再使用（用户 2026-11-08 决定）**：管理表格没有每个人的详细资料；实机上读表格耗尽让出预算、中断后窗口没关导致机器人停摆。标签暂不采集；
5. 逐个展开分组、逐行点开资料卡，读取 微信号/地区/备注/来源/添加时间/共同群聊；资料卡读完立即点下一行，不点资料卡上的任何按钮；
6. 写库：按微信号新建或更新；把备注、昵称登记为名字；
7. 核对：每个分组读到的人数 = 分组标题上的数量，不一致就报"未完整同步"并列出哪个分组差几个，不假装成功；
8. 切回聊天页，恢复自动回复。

预计：约 70 人，资料卡每人约 1.5 秒，总共 2～3 分钟。

**增量同步**（每天一次，在没有待回复消息的空闲时段；或手动 `contacts-sync`）：
1. 展开各分组，只读列表上的名字（不点资料卡）；
2. 与库比较：列表名字（备注或昵称）库里没有的 = 新增或改了备注；
3. 只对这些名字点开资料卡；
4. 消失的人记 `removed_at`。

**中途有客户发消息**：同步每连续执行 15 秒就让出，回到聊天页处理，下一轮从断点继续（断点记在本地，含已滚动格数）。

**出错**：任何一步出错都先切回聊天页（离开时若管理窗口开着先关掉），清掉断点、写明错误，**不自动续做**；协调器断开重连以重新打开目标会话。

## 7. 隐私

- 通讯录资料只存在专用 Mac 本地的聊天历史库（权限 0600）；
- 读取用本机 Vision 文字识别，截图用完即删，不送模型、不走云端识图；
- 日志里不写联系人名字/微信号，只写数量和结果（如"personal 22/22"）；
- 给外部大脑的 MCP 工具只返回允许名单内联系人的资料（与现在的历史查询边界一致）。

### 8.3 界面实现约束

- 仍是原生 macOS 应用（Swift / AppKit），不改成网页；同一个签名证书，权限不会因升级丢失；
- 配置读写沿用现有 ConfigForm 逻辑与校验（范围、格式错误提示），不另起一套；
- 实时日志只读文件末尾，不把整份日志读进内存；日志本身不含聊天正文；
- 「请求权限」能弹框的用系统接口弹框，已拒绝的引导到系统设置对应页面。

## 9. 风险

- 资料卡、表格只能靠文字识别：标签和值会粘在一起（实测），按已知字段前缀拆分；识别错一个字会导致微信号不对 → 同一人两次同步读到的微信号不一致时不覆盖，标记待确认；
- 通讯录较大（上千人）时初始化可能要 30 分钟以上，需要分批、可中断；
- 微信升级后通讯录界面位置可能变化 → 位置写进布局图（`layout`），校准流程一并覆盖；
- 同步期间不能自动回复；增量同步只在空闲时做，并且每个联系人之间检查新消息。
