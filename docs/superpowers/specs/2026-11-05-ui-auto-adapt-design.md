# 微信界面自动适配设计

日期：2026-11-05
状态：待审

## 1. 背景与目的

白名单客服 Bot 目前只认一种画面：微信 4 深色主题、880×640 窗口、1 倍像素（`native/wechat_bubbles.swift` 的 `analyzeFrame`、`native/bot/Sessions.swift`）。系统外观自动切到浅色就会停（2026-11-05 早上停了近 3 小时），而目标用户大多用 Retina 屏的 MacBook，浅色、深色都有。

本项目让 Bot 在 **Retina / 1 倍屏 × 浅色 / 深色** 四种组合下都能工作，用户不必手动改系统或微信设置。这是个人微信辅助工具商业化的第一个前提（稳定交付给别人用）。

## 2. 目标

- G1：浅色、深色主题都能完整工作：基线、收文本/图片/文件、生成并发送回复、回显确认、点击切换会话、未读红点检测。
- G2：Retina（2x）与 1 倍屏都能工作，包括窗口在 Retina 内置屏与 1 倍外接屏之间移动的情况（按窗口当前所在屏的实际像素倍率处理）。
- G3：窗口尺寸固定为 880×640（逻辑点）。不是这个尺寸时，Bot 自动调回；调不回就等待重试。
- G4：运行中切换主题、把窗口移到另一块屏，不需要重启 Bot。
- G5：识别不出时（未知主题、微信改版、窗口异常）不误读、不发送，进入 `waiting_for_wechat_window` 每轮重试（沿用 `coordinator.WINDOW_UNAVAILABLE` 机制）。

## 3. 非目标

- 任意窗口尺寸的解析（用户已同意固定 880×640）。
- 微信 4.1.15 以外版本的兼容保证；Windows 版微信。
- 通用自动标定（自动学习新主题的颜色）。浅色规则是人工标定的一套固定参数。
- 微信内"字体大小"等其他显示设置的适配；默认字体大小以外视为未知画面（按 G5 处理）。

## 4. 反目标（技术上能跑但算失败）

- 主题判断错了还继续解析，把背景块当成气泡、把对方消息当成自己的（方向判反）。方向判错比停下来更糟。
- 调整窗口时和用户抢窗口：用户正在拖动、全屏或最小化时反复强行改窗口。
- 为了 Retina 去改所有坐标常量，导致 1 倍屏原有表现回退。

## 5. 约束

- 微信版本：4.1.15（远端测试机与本机一致）。
- 系统：远端 macOS 12.7.6 x86_64（1 倍屏 1280×1024）；本机 macOS 27.2（内置 Retina 2560×1600 + 外接 1 倍 2560×1440）。
- Swift worker 仍在目标机本地用 `swiftc -O -parse-as-library -D BOT_WORKER` 编译，最低 macOS 12。
- Python 侧保持标准库，测试用 `unittest`。
- 不注入微信进程、不改客户端，只读窗口截图 + 辅助功能接口（调整窗口、点击）。
- 已知风险：本仓库曾为 macOS 26+ 把 OCR 回退到 Tesseract（提交 7e7a699），而 worker 的 `recognize` 用的是 Vision。macOS 27 上 Vision 识别是否可用要先验证；不可用时需要同样的回退方案。计划阶段第一步先确认。

## 6. 已定的做法

### 6.1 窗口尺寸固定（G3）

- 每次截图前检查选中微信窗口的逻辑尺寸。不是 880×640 时，用辅助功能接口（`kAXSizeAttribute`）设回 880×640，再重新取窗口信息核对；核对通过才继续截图。
- 只处理"普通窗口但尺寸不对"。窗口最小化、全屏、不在屏幕上时不强行恢复，返回窗口不可用错误，按 G5 等待重试。
- 一轮内只调一次；调回失败（例如用户正在拖动）也按 G5 处理，不在一轮内反复重试。
- 只改尺寸，不动窗口位置；调整后窗口超出屏幕可见区域的，视为不可用。
- 需要辅助功能权限；worker 点击切换会话时已经要求该权限（`AXIsProcessTrusted`）。
- 只调整微信主窗口：用辅助功能接口取微信的主窗口（`AXMainWindow`），并与截图选中的窗口核对是同一个。打开了图片查看、文件预览、独立聊天等多个窗口、分不清哪个是主窗口时，不调整，按 G5 等待（设计者决定）。

### 6.5 OCR 速度（macOS 26+）

- 实测（本机 macOS 27.2，880×640 微信窗口截图）：Vision 高精度模式**首次**识别约 29 秒（加载模型的冷启动），之后每帧约 0.35 秒；快速模式 0.1 秒，但中文全部识别成乱码，不能用。
- 结论（设计者决定）：继续用 Vision 高精度模式，不引入 Tesseract。解决冷启动：worker 启动时先用一张小图预热识别模型，预热允许最长 60 秒；正式识别保持 12 秒超时。`vision_timeout` 加入 `WINDOW_UNAVAILABLE`，偶发超时按 G5 重试，而不是暂停。
- 目标：预热完成后单帧识别（含会话列表）在 3 秒以内。

### 6.6 新系统截图方式（macOS 15+）

- 现状：`BotWorkerMain` 在 macOS 15+ 直接拒绝启动（`legacy_capture_worker_requires_macOS12_14`），因为截图用的 `CGWindowListCreateImage` 在新系统上已停用。Retina MacBook 用户多数是新系统，不解决就达不到 G2。
- 做法（设计者决定，写计划时发现的范围补充）：把"截取微信窗口图像"收拢成一个函数。macOS 14+ 用 ScreenCaptureKit（`SCScreenshotManager.captureImage`，按窗口截取）；macOS 12–13 继续用 `CGWindowListCreateImage`。窗口枚举（`CGWindowListCopyWindowInfo`）在新系统仍可用，保持不变。去掉 macOS 15 的启动拒绝。
- ScreenCaptureKit 是异步接口；worker 用信号量等待，超时 5 秒报 `window_capture_failed`（已在 `WINDOW_UNAVAILABLE` 中）。
- 需要"屏幕录制"权限；新系统可能定期要求用户重新确认。权限缺失或被拒时返回 `window_capture_failed`，日志写明原因，留给"一键安装"和"异常提醒"项目引导用户处理。

### 6.2 Retina 归一化（G2）

- 解析统一在 880×640 的 1 倍坐标上做，沿用现有所有坐标常量（标题区、聊天区、会话列表区、输入分隔线等）。
- 截图后按 `图像像素宽 / 窗口逻辑宽` 得到倍率：倍率为 1 直接用，否则缩放到 880×640 再解析。倍率每次截图实时计算，所以窗口在两块屏之间移动也自动适配。
- 点击坐标本来就是逻辑点（窗口原点 + 逻辑偏移），不受倍率影响。
- 客户发来的图片：在原始分辨率截图上按同一区域（坐标乘以倍率）裁剪存档，保证清晰度，供模型读图和存档。
- 缩放后的文字边缘、气泡边缘会和原生 1 倍屏略有差异。颜色阈值和最小区域面积要用 Retina 真实截图验证，必要时调参，但不能让 1 倍屏的现有测试回退。

### 6.3 主题识别与两套规则（G1、G4）

- 把现在散落的颜色判断抽成"主题规则"：背景色、自己气泡（绿色）、对方气泡、未读红点、会话列表选中高亮、时间/系统提示文字颜色等。现有深色参数原样搬进 `wechat-4-dark` 规则，行为不变。
- 新增 `wechat-4-light` 规则，参数用真实浅色截图人工标定。
- 每帧先识别主题：在聊天区和会话列表区取样背景色，命中深色或浅色规则的背景特征才继续；两者都不像就报 `uncalibrated_theme`（已在 `WINDOW_UNAVAILABLE` 中，自动重试）。
- 主题按帧识别，不跨帧缓存，所以运行中切换主题自动生效（G4）。
- 截图缓存的 hash 要包含所用规则名，切换主题后不会复用旧解析结果。
- 消息方向（自己/对方）判断在两种主题下都要有专门测试，这是反目标里最严重的错误。
- 气泡指纹 `(direction, digest)` 中，文本和图片气泡的 digest 是框内像素的 SHA256，文件气泡用文件名加大小。切换主题或窗口在 Retina 与 1 倍屏之间移动后，像素会变，指纹全部对不上，会触发连续性断档。**用户决定（2026-11-05，方案 A）**：接受这一点，不改指纹算法、不动历史库。断档按现有机制处理：两帧一致后以当前画面重建基线，不回复，记录 `continuity_gap_rebaseline`。代价是切换那一刻前后到达的消息只记录、不回复。缓解办法：系统外观建议固定，日志里带上切换前后的 `profile`/`scale`，留给后续"异常提醒"项目通知用户。

### 6.4 健康状态

- 返回给 Python 的帧结果里带上 `profile`（`wechat-4-dark` 或 `wechat-4-light`）和 `scale`（1 或 2），写入日志，便于排查。`policy.check_frame` 改为接受这两个 profile、`scale ∈ {1, 2}`。Python 与 worker 同时升级，不保留旧名 `wechat-4-dark-1x`（设计者决定）。
- 窗口被自动调回尺寸时记录一次 `window_resized` 事件。

## 7. 标定与测试数据

- 浅色标定：把远端测试机临时切到浅色，在白名单测试联系人（文件传输助手、测试好友）里制造各类画面：文本、长文本、图片、文件、表情、时间分隔、系统提示、未读红点、选中/未选中会话行。期间 Bot 暂停回复，约半小时，完成后切回深色。对方消息由用户用测试好友账号配合发送；远端的切换和截图由实现者通过 SSH 完成。
- Retina 标定：在本机（Retina）用同一类画面采集深色和浅色截图，并把窗口拖到外接 1 倍屏再采一组。用户在本机登录测试微信号，或只打开文件传输助手；原始截图只在本机临时目录使用，用完删除。
- 进入仓库的测试样本只能来自测试账号的测试会话，不得包含真实客户聊天、头像或其他联系人的会话列表内容；会话列表中非测试联系人的区域在入库前涂掉。

## 8. 验收标准

在以下四个环境各跑一遍：远端 1 倍深色、远端 1 倍浅色、本机 Retina 深色、本机 Retina 浅色。每个环境：

1. 首次接入建立基线，不回复历史。
2. 收到文本、图片、文件后正确生成并发送一条回复，回显被确认。
3. 两个白名单联系人之间靠未读红点切换，点击切换成功。
4. 消息方向全部正确（不把自己的回复当成客户消息）。

另外：

5. 运行中切换浅色/深色，Bot 不重启，一到两轮内恢复工作（切换时可能重建基线，见 6.3）。
6. 手动把微信窗口拉大，Bot 自动调回 880×640 并继续；最小化时进入等待，恢复后继续。
7. 窗口从 Retina 内置屏拖到 1 倍外接屏，Bot 继续工作。
8. 原有 Python 与 Swift 相关测试全部通过，1 倍深色行为无回退。

## 9. 留给实现者决定

- 主题规则在 Swift 中的具体数据结构，取样点的位置和数量。
- 缩放算法（Core Graphics 插值方式）以及阈值的具体微调数值。
- 浅色规则各项颜色参数的具体数值（来自标定）。
- 本机 Retina 测试时 Bot 如何连接本机 worker（例如 SSH 到本机），只要不影响远端部署方式。
