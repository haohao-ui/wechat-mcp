# 微信客服助手：Rust 单服务与可插拔大脑 —— 设计

日期：2026-11-07　分支：feat/wechat-bot-history　状态：待确认（只出方案，未实施）

## 1. 为什么做

用户原话（2026-11-07）：

> 如果把 python 的直接换成 rust 写……可以整合一个微信客服助手上，这套单独运行，完成整体服务。做一个开关，关闭就通过 mcp 或者外部自定义的大脑接管自动回的内容。因为要真正做这个客服 bot 还有专业的知识库。现在核心就是提供这个工具操作微信。

这次改动的核心定位：**本项目是"操作微信的工具"，回复内容由大脑决定，而大脑可以替换。** 专业知识库属于大脑，放在外部。

今天的问题（都在真机上遇到过）：

- **一共三套程序。** Python 机器人（约 3200 行）、Rust wechat-mcp、Swift worker，部署、日志和权限都要各管一份。
  - 2026-11-06：开发机上的机器人跑的还是旧代码，没人发现。
  - 2026-11-06：专用 Mac 用系统自带的 Python 3.9，机器人一启动就崩溃。
- **两套"眼和手"同时操作一个微信窗口。**
  - Rust 负责发消息：点输入框、粘贴、核对、回车。
  - Swift worker 负责其他所有操作：截屏、识别、切换会话、下载。
  - 两边互不知道对方在做什么，标题核对也用的是两套算法。
- **键盘操作还没有并入动作组件。**
  - 2026-11-07：发送按键靠 System Events 代按；剪贴板用 `pbcopy` 读写，但在 launchd 启动的环境下没有 UTF-8，中文变成乱码。
  - 发消息的按键已经临时改走动作组件（提交 1686dd3、b700188），发文件、搜索、⌘1、Esc 还没有改。
- **工具逻辑写在 Python 里。** Python 的 3200 行中，真正属于"大脑"的只有约 370 行：
  - 大脑：`reply.py`、`model_api.py`、`documents.py`；
  - 其余约 2800 行都是"怎么可靠地操作微信"：监听、切换会话、凑齐一轮消息、核对发送结果、暂停与恢复、管理命令。

## 2. 目标 / 非目标 / 反目标

**目标**
- G1 **一个服务完成全部工作**：
  - 微信客服助手（Swift 外壳）负责界面、权限和保活；
  - 它启动一个 Rust 服务，由这个服务完成监听、调度、记账和发送；
  - 运行时不再需要 Python。
- G2 **只保留一套"眼和手"**：只有 Swift worker 操作微信窗口，Rust 不再自己点击或按键。
- G3 **大脑开关**：
  - 开：使用内置大脑，即直接调用兼容 OpenAI 接口的模型，也就是今天的 DeepSeek 用法；
  - 关：由外部大脑提供回复内容。外部大脑可以通过 MCP 主动取消息，也可以通过 Webhook 接收推送。
- G4 **无论大脑是哪一个，安全规则都由服务执行**：
  - 允许名单、限流、冷却、发送前核对标题和输入框、幂等去重、发送结果核对；
  - 大脑只决定"回什么"，不能决定"发给谁"，也不能绕过这些检查。
- G5 **迁移期间不停服务**：Python 机器人一直跑到 Rust 版本完成影子运行、确认结果一致为止。

**非目标（本期不做）**
- 知识库、角色、技能本身。它们属于外部大脑。
- Windows 版的眼和手。本期只把 worker 协议写成和平台无关，见第 6 节 P5。
- 在局域网上开放 TCP 端口。
- 企业微信、公众号。

**反目标**（技术上实现了也算失败的情况）
- 重写过程中丢掉 Python 测试里积累的真机经验，比如连续性断档、回显核对、一轮消息何时结束、发送结果核对。
- 外部大脑能让服务把消息发给允许名单以外的人，或者绕过发送前的核对。
- 切换过程中出现重复发送，或者漏回消息却没有任何记录。

## 3. 目标架构

```
微信客服助手.app（Swift 外壳：状态面板、权限、配置、开关；LaunchAgent 保活）
 └─ wechat-cs-core（Rust，单进程，常驻）
     ├─ 调度：盯允许名单里的会话，看红点或预览变化后切换，凑齐一轮消息
     ├─ 记账：发件箱、幂等去重、发送状态、历史库（沿用现有 SQLite）
     ├─ 大脑接口 ──┬─ 内置大脑：兼容 OpenAI 的模型调用（今天的提示词和上下文条数原样迁移）
     │             └─ 外部大脑：MCP 工具 next_turn / reply，或 Webhook
     ├─ 对外 MCP：保留现有工具（send_message、get_messages、get_send_status 等），新增大脑相关工具
     └─ 眼和手：调用 Swift worker（唯一操作微信的程序）
          wechat_bot_worker：截屏和识别、会话列表、打开会话、滚动、取图和文件、
                             发送文字（新增）、发送文件（新增）、按键和点击（动作组件）
```

要点：

- **Rust 服务由助手启动，常驻运行**，不再是"来一个连接启动一个进程"。
  - 这样状态面板看到的就是真实运行状态，不会再有"机器人核心查不到"的情况。
  - 外部 MCP 客户端仍然通过 `~/.wechat-rpa/worker.sock` 连进来，同一时间可以有多个连接。
- **服务启动时一律显式设置 UTF-8 语言环境**，同时保留 `src/clipboard.rs` 里已有的保护。
- **发送流程整体移进 Swift worker**，新增操作 `send_text` 和 `send_file`：
  1. 在本会话内核对标题；
  2. 点输入框；
  3. 全选，再粘贴替换原有内容（以前是直接追加，失败后会留下残余）；
  4. 读回核对；
  5. 核对一致才按回车；核对失败就清空输入框，再返回"未触发发送"。

  剪贴板改用 `NSPasteboard` 直接读写，不再经过 `pbcopy`。Rust 只负责记账、调用 worker 和记录结果。
- **按真机观察的规矩**：`send_text` 里"全选替换"和"失败清空"这两个新动作，要先在测试群录一遍，确认微信的反应，再写代码。

## 4. 大脑开关与接口

### 4.1 开关
- 配置项 `brain.mode`：`builtin`（默认，即今天的行为）或 `external`。
- 面板上有对应的开关。切换时立即生效：
  - 已经交给大脑、还没回来的那一轮，按原来的模式完成；
  - 下一轮按新模式处理。
- 按联系人单独设置开关：留作可选项，见第 8 节问题 2。

### 4.2 一轮消息（turn）的数据
服务交给大脑的，是"一轮客户消息"及其上下文：

```json
{
  "turn_id": "t_…",                 // 也是发送时的幂等键
  "account_id": "test-desktop",
  "contact": {"name": "测试群", "kind": "group"},
  "messages": [{"kind": "text", "text": "…", "sender": "…", "observed_at": "…"},
               {"kind": "image", "media_id": "…"}, {"kind": "file", "media_id": "…", "filename": "…"}],
  "context": [/* 最近 N 条历史，含我方回复，和今天 context_messages 相同 */],
  "deadline_at": "…"                // 超过这个时间还没回复，按第 4.4 节处理
}
```

图片和文件只给 `media_id`。大脑需要时再用 MCP 工具 `read_media` 取内容，取的时候受附件大小上限约束。

### 4.3 外部大脑的两种接入方式
- **MCP 拉取（首选）**：新增工具
  - `next_turn(wait_seconds)`：长轮询，有新的一轮就返回，没有就等到超时返回空；
  - `reply(turn_id, action, text?, files?)`，`action` 取以下之一：
    - `send`：发送；
    - `skip`：这一轮不回复；
    - `handoff`：转人工。会话进入"等待人工"状态，服务继续记录消息，但不再交给大脑，直到人工恢复。
- **Webhook 推送（可选）**：服务把 turn 以 POST 发到配置好的地址，大脑在响应里直接返回和 `reply` 相同的内容。
  - 只允许 `https`，或者本机地址 `http://127.0.0.1`；
  - 请求带共享令牌签名。
- 两种方式可以同时开着：同一个 turn 以最先到达的 `reply` 为准，之后再到的视为重复，直接拒绝。

### 4.4 安全边界（无论哪种大脑）
- `reply` 只能回复服务交出去的那个 turn，发送对象是 turn 里的联系人，大脑无法指定别的接收人。
- 回复都要经过同样的发送前检查：
  - 允许名单；
  - 每小时回复上限和冷却时间；
  - 这一轮之后是不是已经有人回复过（排除自己的发送尝试）；
  - 标题核对和输入框读回核对。
- 外部大脑超时：默认 `skip` 并记录原因，可以改成"改用内置大脑"或"转人工"。
- 外部大脑不在线：turn 进入等待队列，最多保留 N 分钟（可配置），过期后按超时处理。面板上会显示"外部大脑未连接"。

## 5. Python → Rust 迁移

按模块迁移。每个模块迁移时，把对应的 Python 测试一起翻译成 Rust 测试，翻译后的测试全部通过，这个模块才算迁完。

| 模块（Python） | 行数 | 去向 |
|---|---|---|
| coordinator.py（多会话调度、红点和预览、会话切换） | 517 | Rust `core::scheduler` |
| service.py（一轮消息、日志记录、发送与核对、暂停与恢复） | 927 | Rust `core::turns` 和 `core::delivery` |
| native_capture.py（worker 客户端） | 340 | Rust `core::worker_client` |
| policy.py（画面检查、回显比对、校准） | 214 | Rust `core::policy` |
| capture.py / routing.py / transport.py | 约 180 | Rust，或者在常驻单进程下直接删掉 |
| control.py（管理命令） | 592 | Rust 子命令，加上面板按钮 |
| history/（历史库，HTTP 和 MCP 读取） | — | Rust 直接读写同一个 SQLite，表结构不变 |
| reply.py / model_api.py / documents.py | 约 370 | Rust `brain::builtin`，提示词逐字照搬 |

**状态和数据不迁移格式**：日志文件、游标、历史库、发件箱都沿用现有文件和表，Rust 版本读同样的东西。这样切换过去和切换回来，都只是换一个进程。

**影子运行**：Rust 调度器先以"只看不发"的模式和 Python 并行运行，记录它对每一轮的判断：
- 是否开一轮、何时结束这一轮；
- 应该回复还是跳过；
- 是否已经有人回复过。

然后和 Python 的实际结果逐条比对。连续 3 天没有差异（或者差异都能解释），再切换。

## 6. 分阶段计划

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| P1 统一眼和手 | 先在测试群录一遍"全选替换"和"失败清空"；worker 新增 `send_text` 和 `send_file`（NSPasteboard 加动作组件按键）；Rust 的 `send_message` 和 `send_file` 改为调用 worker；搜索、⌘1、Esc 这些按键也改走动作组件 | Rust 里不再有 System Events 按键和 `wechat_click` 调用；测试群里文字和文件都能正常收发 |
| P2 Rust 核心（内置大脑） | 按第 5 节迁移，翻译测试；助手启动常驻的 Rust 服务 | Rust 测试覆盖翻译过来的 Python 用例；影子运行 3 天没有无法解释的差异 |
| P3 切换 | 停掉 Python 机器人，由 Rust 接管；Python 保留一周，随时可以切回 | 第 7 节验收全部通过 |
| P4 外部大脑 | `brain.mode`、`next_turn`/`reply`、Webhook、超时策略、转人工；面板加开关 | 用一个示例外部大脑（脚本或 MCP 客户端）在测试群跑通 send、skip、handoff 和超时 |
| P5 平台无关的协议文档 | 把 worker 协议（操作、参数、错误码）写成文档，为将来 Windows 版的眼和手做准备 | 文档评审通过 |

P1 本身就能独立带来价值，因为它解决的正是今天出过的事故。P2 和 P3 工作量最大。P4 依赖 P2 里的大脑接口。

## 7. 验收（P3、P4 结束时，在专用 Mac 上验证）
1. 只运行助手一个程序（不装 Python 机器人）：测试群、午夜咖啡、文件传输助手三个会话都能正常监听和回复，文字、图片、文件都覆盖到。
2. 发送失败时：只要还没按回车就自动重试，会话不会暂停；回车以后结果不确定的，先看屏幕核对，不会重复发送。
3. 助手的启动方式不影响结果：分别通过 launchd、访达、终端启动，中文都不会乱码。
4. 外部大脑：
   - 关掉开关后，回复由外部大脑提供；
   - 外部大脑指定发给别人时会被拒绝；
   - 超时后按配置处理；
   - 转人工后，会话不再自动回复，直到人工恢复。
5. 面板上的"机器人核心"显示的是 Rust 服务的真实状态，开关可以正常切换。

## 8. 需要你决定的问题
1. **和《微信自动化客服控制台》设计（2026-11-06-wechat-cs-console-design.md）的关系。**
   - 那份设计是在 Python 机器人上加知识库、角色和人工接管。
   - 我的建议：把它改定位为"外部大脑加管理界面"，通过第 4 节的接口接进来。那份设计里的人工接管，对应这里的 `handoff`。
   - 你同意的话，那份文档需要由它的作者按这个定位修改。
2. **开关是全局一个，还是每个联系人可以单独设置？** 建议先做全局，同时预留按联系人设置的配置项。
3. **外部大脑超时后的默认做法**：不回复（skip）、改用内置大脑、还是转人工？我建议默认不回复，因为不回比回错安全。
4. **v1 要不要做 Webhook？** 还是只做 MCP 拉取？我建议 v1 只做 MCP，Webhook 放到 P4 后半段。
5. **P1 先做，还是 P1 和 P2 并行？** 我建议先做 P1。它风险小、见效快，也是 P2 的基础。
