# 微信客服助手（专用 Mac 管理程序）+ 机器人迁到专用 Mac —— 设计

日期：2026-11-06
状态：待用户审阅

## 1. 为什么做

- 微信那台 Mac 上的宿主程序还叫 "WeChat RPA Test"，界面只有"环境检查"和三个按钮，不像一个能交付的产品。
- 日常维护全靠我 ssh 上去敲命令。本次真机上就碰到了两次，而且都是用户看不到、也处理不了的：
  1. 宿主程序退出后，机器人一直重连；最后是远程执行 `open` 才恢复的。
  2. 一个藏在主窗口后面的微信下载窗口，让机器人一直等待。
- 机器人本体现在跑在开发电脑上，通过 ssh 去操作微信那台 Mac。用户已经定下来：**机器人整体搬到专用 Mac 上**，2026-11-06 选了方案 A。这样所有东西都在同一台机器上，助手可以直接读写配置。

## 2. 目标

- G1 改名：显示名"微信客服助手"，`微信客服助手.app`，bundle ID `local.wechat-mcp.host`。
- G2 状态面板：一眼看出机器人能不能正常工作；不能的话，原因是什么、该谁来处理。
- G3 自动启动与保活：登录后自动启动；助手和机器人意外退出后自动拉起。
- G4 一键操作：重启服务、把微信窗口放回标准位置、打开附件文件夹、打开日志文件夹、暂停/恢复机器人。
- G5 常用配置：在助手里修改白名单、附件大小上限、回复限流、轮次等待时间。保存前先校验，保存后机器人自动生效。
- G6 机器人迁移：机器人、历史库和游标都搬到专用 Mac。开发电脑以后只负责开发和部署。

## 3. 非目标

- 不做 DSH 控制台。那份设计是 `2026-11-06-wechat-cs-console-design.md`，它以后可以远程读同一份数据。
- 不改 Rust MCP 对 Agent 的工具契约（`tools/list`）。
- 不做"眼 / 手 / 脑 / 记账"的重构，那是另一份设计，依据是 `docs/observations/2026-11-06-wechat-4.1.15-actions.md`。
- 不在助手里编辑模型密钥，也不在助手里显示模型密钥。

## 4. 不能做成的样子（反目标）

- 助手自己去点微信、读聊天内容。它只读窗口元数据和机器人的健康状态文件，不截取聊天画面。
- 保活变成"疯狂重启"。崩溃后要有退避，一直起不来就停下，并在面板上说明原因。
- 改配置时写坏文件，导致机器人起不来。必须先校验，再原子写入，并保留备份。
- 迁移途中两台机器上的机器人同时在跑，导致重复回复。

## 5. 设计

### 5.1 改名与重新授权（G1）

- `Info.plist`：
  - `CFBundleName` 和 `CFBundleDisplayName` 改为"微信客服助手"；
  - `CFBundleIdentifier` 改为 `local.wechat-mcp.host`；
  - 可执行文件名改为 `wechat-cs-host`；
  - 窗口标题改为"微信客服助手"。
- 安装位置：`~/Applications/微信客服助手.app`。旧的 `WeChat RPA Test.app` 先退出，再挪到 `~/Applications/.old/`，不删除，以便回滚。
- macOS 的权限记录跟着 bundle ID 和签名走，所以改名后**必须重新授权**：
  - 用户要在专用 Mac 上，到"系统设置 → 隐私与安全性"里重新勾选"屏幕录制"和"辅助功能"；
  - 授权完成后，助手里点"刷新检查"，确认两项都通过；
  - 这一步不能远程代劳。
- `worker.sock` 的路径和协议不变，机器人那边不用改。

### 5.2 状态面板（G2）

每 5 秒刷新一次。每一项显示为 绿 / 黄 / 红，附一句中文原因，红色项再给"怎么处理"。

| 项 | 数据来源 | 红/黄的例子 |
|---|---|---|
| 权限 | 现有 `Probe.swift` | 屏幕录制未授权 |
| 桌面服务 | `worker.sock` 是否在监听，MCP 子进程是否存活 | 服务未启动 |
| 机器人 | launchd `local.wechat-rpa.bot` 是否加载；`health.json` 的 state 和更新时间 | 超过 2 分钟没有更新；needs_recalibration；paused |
| 各会话 | `health.json` 的 sessions | waiting_for_wechat_window，原因是 `screen_not_main:other_wechat_window` |
| 微信 | 进程、版本、主窗口位置和大小、有没有其他微信窗口挡在主窗口**前面** | 窗口不在标准位置；有窗口挡住 |
| 布局地图 | `~/.wechat-rpa/layout/wechat-<版本>.json` 是否存在 | 当前版本没有地图 |
| 磁盘 | 附件文件夹大小、剩余空间 | 剩余空间不足 5GB |

只读 `health.json` 里的状态字段，不读消息内容。会话名属于白名单内的名字，可以显示。

### 5.3 自动启动与保活（G3）

- **助手**：用 LaunchAgent `local.wechat-mcp.host` 在登录后启动，设置 `KeepAlive={SuccessfulExit:false}` 和 `ThrottleInterval=30`。
  - 用户主动点"退出"时正常退出，不会被拉起；
  - 崩溃时 30 秒后自动拉起；
  - 用 LaunchAgent 而不是 `SMAppService`，因为 macOS 12 没有 `SMAppService`。
- **机器人**：沿用现有 launchd `local.wechat-rpa.bot`，安装到专用 Mac。
  - 助手不重复做保活，只负责显示状态，并提供"重启机器人"按钮。
- **桌面服务子进程**：由助手托管。子进程退出后，助手按 5 秒、15 秒、60 秒的间隔退避重启；同一小时内失败 5 次就停止重启，面板显示红色。
- 这样修好了本次的问题："一结束 worker 进程，宿主就不见了"。原因还没查清，计划在实现时先补日志，再复现一次。

### 5.4 一键操作（G4）

| 按钮 | 做什么 | 安全约束 |
|---|---|---|
| 重启桌面服务 | 由助手结束并重启它自己托管的 MCP 子进程，不再靠远程 `pkill` | 机器人正在发送时先确认 |
| 重启机器人 | `launchctl kickstart -k gui/<uid>/local.wechat-rpa.bot` | 同上 |
| 暂停 / 恢复机器人 | 写 `control pause` / `resume`，需要新增这两个子命令 | 暂停期间不读、不点、不回复 |
| 微信窗口放回标准位置 | 复用 worker 的 manage_window 逻辑：取消最小化，大小 880×640，坐标固定 | 只移动窗口，不点击窗口内容 |
| 打开附件文件夹 / 日志文件夹 | 在访达里打开 | — |
| 复制诊断信息 | 把状态面板内容复制为文本，方便发给维护人员 | 不包含消息内容和密钥 |

### 5.5 常用配置（G5）

- 可编辑的字段：
  - `allowlist`、`ignorelist`；
  - `max_attachment_mb`，1～200；
  - `max_replies_per_hour`、`cooldown_seconds`、`turn_quiet_seconds`、`turn_max_seconds`、`context_messages`；
  - `manage_window`。
- 只读显示的字段：`account_id`、`model_config.backend` 和 `model_config.model`。密钥只显示"已配置 / 未配置"。
- 保存流程：
  1. 写入临时文件；
  2. 用 `python3 -m scripts.wechat_bot.control config-check <临时文件>` 校验。这个子命令是新增的，内部调用现有的 `load_config`，校验规则只有这一份；
  3. 校验通过后，把旧配置备份为 `config.json.bak-<时间戳>`，再原子替换；
  4. 重启机器人，配置生效。
- 校验失败时，在对应字段下方显示中文原因，不写入任何文件。

### 5.6 机器人迁移到专用 Mac（G6）

- **运行环境**：专用 Mac 上的系统 Python 是 3.9.6。
  - 现有代码用 3.9 编译能通过，但 `scripts/agent_bridge/mcp.py:30` 用了 3.11 才有的 `asyncio.timeout`，运行时会出错；
  - 要改成 `asyncio.wait_for`，并在专用 Mac 上用 3.9 跑一遍全量测试；
  - 机器人只用了标准库，不需要安装依赖。
- **本机模式**：配置里的 `host` 允许写 `"local"`。
  - 这时连 worker 直接执行 `/usr/bin/nc -U ~/.wechat-rpa/worker.sock`，不经过 ssh；
  - calibrate 等远程命令也改为在本机执行。
- **安装位置**：
  - 代码装到 `~/.wechat-rpa/bot/`，作为部署副本，不放 git 工作区；
  - 配置 `~/.WeChatRPABot/config.json`；
  - 状态目录 `~/Library/Application Support/WeChatRPABot/`，大约 32MB，含历史库、游标和日志。
- **模型密钥**：配置里用的是 `api_key_env`。
  - 迁移时由用户自己在专用 Mac 上把密钥写进 LaunchAgent 的环境变量，或者写进钥匙串，由启动脚本读取；
  - **不经过聊天、不经过开发电脑**。
- **切换步骤**（保证同一时刻只有一个机器人在跑）：
  1. 停掉开发电脑上的机器人，并确认 launchd 已卸载；
  2. 把状态目录复制到专用 Mac；
  3. 在专用 Mac 上执行 `control start`，看状态面板变绿；
  4. 在示例群发一条消息，确认有回复。
- **回滚**：停掉专用 Mac 上的机器人，开发电脑执行 `control start`。开发电脑上的状态目录原样保留。
- **部署**：开发电脑上新增 `scripts/deploy_host.sh`，把代码、worker 和助手一次推到专用 Mac。推之前先备份旧版本，推完后由助手重启服务，不再远程 `pkill`。

## 6. 留给实现者决定

- 状态面板用 AppKit 手写，不引入 SwiftUI（macOS 12 + Swift 5.7 可以用 SwiftUI，但现有代码都是 AppKit）。
- 刷新间隔、颜色阈值可以按实际情况微调。
- 诊断信息的具体文本格式。

## 7. 验收（真机）

1. 改名后重新授权，状态面板全部变绿。
2. 在活动监视器里强制结束助手，30 秒内自动回来，机器人自动恢复连接。
3. 在助手里把附件上限改成 60 并保存，`health` 里机器人重启，配置生效；故意输入 0，保存会被拒绝，并显示原因。
4. 拖走微信窗口后点"放回标准位置"，窗口回到原位，机器人继续工作。
5. 迁移完成后关掉开发电脑，示例群里机器人照常回复。
