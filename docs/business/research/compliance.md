## 0. 执行摘要

### 0.1 一句话结论

**当前形态不具备直接商业化的合规基础，属「红色阻断」级。**

决定性的不是"是否只操作自己账号""是否只回复白名单"，而是**技术路线本身已经被微信平台逐项点名**。微信安全中心 2026-01-29《针对第三方违规行为的打击公告》把两类行为单列治理，而本产品同时命中两类：

> **1. 违规获取用户敏感数据类**：通过技术手段（如**录音、录屏、截图、辅助服务读取**、破解数据库等）违规获取用户聊天记录、联系人信息等敏感数据……
> **2. 外挂类**：利用**模拟按键、自动化脚本**等手段操控微信，实现"**自动回复**""**管理聊天记录**""**批量加好友**""虚拟定位"等功能。

本产品的技术栈正是：屏幕**截图** + OCR、**辅助功能/AppleScript** 读取界面、**模拟按键/鼠标**发送消息、**自动化脚本**驱动、**管理聊天记录**、可选**自动回复**。这不是"踩线"，是**逐项对应**。

因此：
- **平台层面**：违规是确定性的，不因账号是自己的、对象是白名单而改变。此外，《腾讯微信软件许可及服务协议》**2.3.1 将使用许可限定为"非商业目的"**——**商业化使用本身即构成违约**，无需等到封号或使用外挂。
- **刑事层面**：纯 UI 自动化（无 Hook / 无注入 / 无协议逆向 / 无数据库破解）的入罪风险**相对较低**，但并非为零，且一旦加入"多开 / 免扫码 / 虚拟定位 / 规避检测"等功能，风险性质会从"违约"跳到"刑事"。
- **民事/行政层面**：封号损失赔偿、腾讯不正当竞争索赔、个人信息保护处罚，三者都有现实先例或明确法条。

### 0.3 五个必答问题速答

| # | 问题 | 结论 | 等级 |

### 1.2 决定法律定性的六个技术问题

商业化前必须由技术团队书面回答，并作为合规档案留存：

1. 是否存在对微信进程的 **Hook / 注入 / dylib 注入 / 内存读写**？（若"是"，刑事风险立即升至红色）
2. 是否读取微信**本地数据库**（如 `MicroMsg.db`）或解密聊天存储？（若"是"，直接命中公告"破解数据库"）
3. 是否使用**辅助功能（Accessibility）/ 屏幕录制**权限读取界面？（已知：是，命中公告"辅助服务读取""截图"）
4. 是否使用**模拟按键/鼠标事件**发送消息？（已知：是，命中公告"模拟按键"）
5. 是否提供或计划提供 **多开、免扫码登录、虚拟定位、批量加好友、自动通过好友申请、养号**？（当前部分存在，风险最高的一组功能）
6. 是否提供**关闭/隐藏 AI 标识**、**规避平台检测**、**修改设备指纹**的选项？（若"是"，可能独立构成违法）

> **判断规则**：问题 1、2 任一为"是" → 直接进入刑事高风险；问题 5、6 任一为"是" → 从"平台违规"升级为"可能被认定为专门用于侵入/非法控制的工具"。

## 2. 红色风险（阻断级）

### R1 平台规则：技术路线被逐项点名

#### R1.1 规范原文

《微信个人账号使用规范》（腾讯官方页面，更新日期 **2026-10-15**）第 1.2 条：

> **1.2.4** 对微信软件或者微信软件运行过程中释放到任何终端内存中的数据、软件运行过程中客户端与服务器端的交互数据，以及微信软件运行所必需的系统数据，进行复制、修改、增加、删除、挂接运行或创作任何衍生作品，形式包括但不限于使用插件、外挂或非经腾讯授权的第三方工具/服务接入微信软件和相关系统；
>
> **1.2.6** 通过非腾讯开发、授权的第三方软件、插件、外挂、系统等，注册、登录、使用微信软件及服务或**进行自动化操作**，对微信软件及其组件、模块、**界面**、数据等进行**访问、读取或控制**，或**制作、发布、传播上述工具、方法**等；
>
> **1.2.7** 自行或授权他人使用第三方软件或系统等对微信软件及其组件、模块、数据进行干扰或破坏，或规避、破坏微信软件设置的安全保护等技术措施；
>
> **1.2.9** 常见的违规行为包括但不限于：**滥用系统权限能力操作微信软件**；使用抢红包插件、外挂、软件或系统；使用微信多开插件、外挂、软件或系统……

第 3.4 条（其他操作异常）：

> 如用户账号在一定期间内产生**异常大量的信息**……或者实施**高频异常行为**，如频繁添加他人为好友、频繁被他人添加为好友、频繁加群、频繁拉群等，存在安全隐患或导致腾讯带宽资源被过度占用的，腾讯将对该等用户启动暂时冻结更新操作……或者采取限制措施，直至账号使用情况恢复正常。

第 4.1 条（数据获取）：

> **未经其他微信用户明确同意**，或未向其他微信用户如实披露数据用途、使用范围等相关信息的情形下**复制、存储、使用或传输其他微信用户数据**，侵害其他微信用户合法权益的。

第五章处理规则第 1 项：

> 对于违反本规范的微信个人账号，一经发现，腾讯将根据情节进行删除或屏蔽违规信息、**警告、限制或禁止使用部分或全部功能直至永久封号、回收账号**的处理，并有权拒绝向违规账号主体提供服务。如：限制与该主体相关账号功能、**封禁与该主体相关账号**、回收账号等，同时，腾讯有权公告处理结果。

**三个要点**：
1. **"界面"被明文写入 1.2.6**——"只读界面、不碰内存"不能再作为抗辩，UI 自动化同样被覆盖。
2. **"制作、发布、传播上述工具"本身即违规**——意味着**卖工具的人和使用工具的人各自违规**，不是只有用户担责。
3. **"限制与该主体相关的账号"**——同一主体（同一实名、同一设备、同一支付）下的其他账号可能被连带处置。

#### R1.2 《腾讯微信软件许可及服务协议》的对应条款（商业化本身即违约）

《腾讯微信软件许可及服务协议》（腾讯官方页面，2026-11-09 取用）与《使用规范》互为补充，其中三处条款对商业化而言比《使用规范》更致命：

> **2.3.1** 腾讯给予你一项个人的、不可转让及非排他性的许可，以使用本软件。你可以为**非商业目的**在**单一台终端设备**上安装、使用、显示、运行本软件。

### R2 刑事风险：刑法第 285 条第 3 款

#### R2.1 法条与司法解释

> **《刑法》第二百八十五条第三款**：提供专门用于侵入、非法控制计算机信息系统的程序、工具，或者明知他人实施侵入、非法控制计算机信息系统的违法犯罪行为而为其提供程序、工具，情节严重的，依照前款的规定处罚。
> （前款：情节严重的，处三年以下有期徒刑或者拘役，并处或者单处罚金；情节特别严重的，处三年以上七年以下有期徒刑，并处罚金。）

> **法释〔2011〕19 号 第二条**：具有下列情形之一的程序、工具，应当认定为刑法第二百八十五条第三款规定的"专门用于侵入、非法控制计算机信息系统的程序、工具"：
> （一）具有**避开或者突破计算机信息系统安全保护措施**，未经授权或者超越授权获取计算机信息系统数据的功能的；
> （二）具有**避开或者突破计算机信息系统安全保护措施**，未经授权或者超越授权对计算机信息系统实施控制的功能的；
> （三）其他**专门设计**用于侵入、非法控制计算机信息系统、非法获取计算机信息系统数据的程序、工具。

**入罪核心 = "避开或突破安全保护措施" + "专门设计"。**

#### R2.3 对本产品的定性分析

**有利事实（降低入罪概率）**：
1. 通过**系统级可见 UI** 操作，不注入进程、不 Hook、不解密数据库、不逆向协议。
2. 使用微信**自身的登录态与密码校验**，未"避开或突破安全保护措施"——这是法释〔2011〕19 号第二条的核心要件。
3. 用户对**自己的账号**有访问权限，读取的是自己屏幕上可见的内容，不构成"未经授权获取"。
4. 慈利县案表明：**是否"专门用于侵入/非法控制"需要检验鉴定**，不能仅凭功能描述推定。

**不利事实（提高入罪概率）**：
1. 微信 2026-01-29 公告已把"截图/辅助服务读取/模拟按键/自动化脚本"定性为"**绕过微信安全技术措施**"。该公告是**平台单方定性**、不是司法认定，但会成为报案、立案、鉴定时的重要材料。
2. 若产品包含**多开、免扫码、虚拟定位、批量加好友、修改设备指纹、规避检测**，将直接落进"专门设计用于……控制"的外观。
3. 若销售规模大（司法解释对"情节严重/特别严重"以程序数量、违法所得、经济损失等量化），一旦定性成立，量刑会随规模上升。
4. 单位销售 → **单位犯罪 + 直接负责的主管人员/其他直接责任人员**双重追责。

**风险概率判断（专家判断，非统计）**：

| 产品形态 | 285 条 3 款立案风险 | 说明 |
|---|---|---|
| 纯 UI 自动化（AppleScript + 键鼠 + OCR），无 Hook、无多开、无规避检测，仅供自用 | **低（<5%–10%）** | 不满足"避开或突破安全保护措施"核心要件 |
| 同上，但**对外销售** | **中低（10%–25%）** | 增加"提供工具"外观 + 平台报案动力；仍缺"突破措施"要件 |
| 加入多开 / 免扫码 / 批量登录 / 虚拟定位 | **中高（30%–60%）** | 接近张尧案、云和案的功能外观 |
| 加入 Hook / 注入 / 数据库破解 / 协议逆向 | **高（>70%）** | 直接命中"突破安全保护措施" |
| 明知客户用于诈骗/赌博仍提供 | **另触犯帮信罪（287 条之二）** | 3 年以下 |

> **关键提示**：刑事风险不是"0 或 1"，而是**功能清单的函数**。产品每增加一个"绕过限制"的功能，就朝红色移动一格。这是产品设计层面可以主动控制的变量。

#### R2.4 其他可能的罪名

- **非法获取计算机信息系统数据罪（285 条 2 款）**：若通过技术手段批量抓取他人通讯录/关系链（而非自己可见界面），可能触发。
- **破坏计算机信息系统罪（286 条）**：若自动化导致微信客户端/服务异常，理论上可能，但本产品场景下概率极低。
- **帮助信息网络犯罪活动罪（287 条之二）**：若客户将此用于电诈引流、赌博，且软件方"明知或应知"（例如提供批量加好友、话术模板、规避封号），风险现实存在。
- **侵犯公民个人信息罪（253 条之一）**：若将 OCR 得到的客户手机号/微信号批量导出、出售或提供——这是**最容易踩到且量刑较重**的罪名（情节特别严重可 3–7 年）。

### R3 个人信息保护：聊天记录 / 图片 / 通讯录

#### R3.1 为什么这是红色

本产品处理的是**第三方（聊天对象）的个人信息**，而合法性基础只能来自：
- 该第三方**本人**的同意；或
- 其他法定情形（合同必需、法定义务等）。

"商家买了软件""商家同意使用"**不能替代**聊天对象本人的同意。这是最容易被创业者忽略、也最容易被监管认定的问题。

同时命中平台规则第 4.1 条："未经其他微信用户明确同意……复制、存储、使用或传输其他微信用户数据"。

#### R3.2 法条原文

> **《个人信息保护法》第十三条**：符合下列情形之一的，个人信息处理者方可处理个人信息：（一）取得个人的同意；（二）为订立、履行个人作为一方当事人的合同所必需……（三）为履行法定职责或者法定义务所必需；（四）为应对突发公共卫生事件，或者紧急情况下为保护自然人的生命健康和财产安全所必需；（五）为公共利益实施新闻报道、舆论监督等行为，在合理的范围内处理个人信息；（六）依照本法规定在合理的范围内处理个人自行公开或者其他已经合法公开的个人信息；（七）法律、行政法规规定的其他情形。

> **第十四条**：基于个人同意处理个人信息的，该同意应当由个人在**充分知情**的前提下**自愿、明确**作出。法律、行政法规规定处理个人信息应当取得个人**单独同意**或者书面同意的，从其规定。个人信息的处理目的、处理方式和处理的个人信息种类发生变更的，应当**重新取得个人同意**。

> **第十七条**（告知义务）：个人信息处理者处理个人信息前，应当以显著方式、清晰易懂的语言真实、准确、完整地向个人告知下列事项：（一）个人信息处理者的名称或者姓名和联系方式；（二）个人信息的处理目的、处理方式，处理的个人信息种类、保存期限；（三）个人行使本法规定权利的方式和程序；（四）法律、行政法规规定应当告知的其他事项。

> **第二十一条**（委托处理）：个人信息处理者委托处理个人信息的，应当与受托人**约定委托处理的目的、期限、处理方式、个人信息的种类、保护措施以及双方的权利和义务**等，并对受托人的个人信息处理活动进行**监督**。

> **第二十三条**（向第三方提供）：个人信息处理者向其他个人信息处理者提供其处理的个人信息的，应当向个人告知接收方的名称或者姓名、联系方式、处理目的、处理方式和个人信息的种类，并取得个人的**单独同意**。

> **第二十八条**：敏感个人信息是一旦泄露或者非法使用，容易导致自然人的人格尊严受到侵害或者人身、财产安全受到危害的个人信息，包括**生物识别、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹**等信息，以及**不满十四周岁未成年人的个人信息**。只有在具有特定的目的和充分的必要性，并采取严格保护措施的情形下，个人信息处理者方可处理敏感个人信息。

> **第二十九条**：处理敏感个人信息应当取得个人的**单独同意**；法律、行政法规规定处理敏感个人信息应当取得书面同意的，从其规定。

> **第五十五条**：有下列情形之一的，个人信息处理者应当**事前进行个人信息保护影响评估**，并对处理情况进行记录：（一）处理敏感个人信息；（二）利用个人信息进行自动化决策；（三）委托处理个人信息、向其他个人信息处理者提供个人信息、公开个人信息；（四）向境外提供个人信息；（五）其他对个人权益有重大影响的个人信息处理活动。

> **第五十六条**：个人信息保护影响评估报告和处理情况记录应当**至少保存三年**。

> **第六十六条**（罚则）：违反本法规定处理个人信息，或者处理个人信息未履行本法规定的个人信息保护义务的，由履行个人信息保护职责的部门责令改正，给予警告，没收违法所得……拒不改正的，并处一百万元以下罚款；对直接负责的主管人员和其他直接责任人员处一万元以上十万元以下罚款。**情节严重的**，由省级以上部门责令改正，没收违法所得，并处**五千万元以下或者上一年度营业额百分之五以下**罚款，并可以责令暂停相关业务或者停业整顿、通报有关主管部门吊销相关业务许可或者吊销营业执照；对直接负责的主管人员和其他直接责任人员处**十万元以上一百万元以下**罚款。

#### R3.3 聊天记录是否属于"敏感个人信息"？

- 聊天记录**整体**不在第 28 条列举范围内，**通常不整体认定为敏感个人信息**。
- 但聊天记录**极易包含**敏感内容：医疗健康（问诊、药品）、金融账户（转账、卡号）、行踪轨迹（地址、定位）、特定身份、以及**不满 14 周岁未成年人**信息。一旦包含，该部分处理即触发**单独同意 + 特定目的 + 充分必要性 + 严格保护措施**。
- 图片（OCR 对象）风险更高：可能含身份证、银行卡、病历、人脸。

**实务结论**：不能假设"聊天记录不是敏感信息"就整体豁免。必须做**内容分级**：默认按可能含敏感信息设计（加密、脱敏、分级授权、最短留存）。

#### R3.4 合法性基础的设计（必须落地的四层链条）

| 层 | 主体 | 义务 | 落地动作 |
|---|---|---|---|
| L1 | 商家（客户） | 作为个人信息处理者，向其消费者告知并取得同意 | 在加好友欢迎语、首次对话、服务须知中明确"会话将被工具辅助处理" |
| L2 | 软件方 | 作为**受托处理者**（个保法 21 条）或独立处理者 | 与商家签 DPA：目的限定、期限、安全措施、禁止二次使用、审计权、删除返还 |
| L3 | 软件方 | PIA（55/56 条） | 出具《个人信息保护影响评估报告》，留存 3 年 |
| L4 | 软件方 | 安全措施（51 条）、最短必要（6/19 条）、境内存储 | 加密、权限分级、日志审计、留存期限、删除机制、不出境 |

> **注意**：若软件方将聊天记录用于**模型训练、话术优化、行业分析**，则从"受托处理者"变为"**独立处理者**"，需要**自己的**合法性基础（通常需单独同意），且属于"处理目的变更"（14 条第 2 款）。这是很多 AI 客服产品实际违法的地方。

#### R3.5 通讯录同步的额外风险

- 好友列表、昵称、头像、备注、手机号 → 均为个人信息。
- 批量导出/同步 → 平台规范 4.1、4.3、4.4 违规；若导出手机号并用于营销 → 可能触犯**侵犯公民个人信息罪**。
- 若通过 OCR 界面批量读取（而非用户逐条授权），"未经授权获取"的认定风险上升。

### R4 生成式 AI 标识义务

#### R4.1 规范体系（三层）

1. **《生成式人工智能服务管理暂行办法》**（2023-08-15 施行）第 12 条：
   > 提供者应当按照《互联网信息服务深度合成管理规定》对图片、视频等生成内容进行标识。
2. **《互联网信息服务深度合成管理规定》**（2023-01-10 施行）第 17 条第 1 款：
   > 深度合成服务提供者提供以下深度合成服务，**可能导致公众混淆或者误认的**，应当在生成或者编辑的信息内容的合理位置、区域进行**显著标识**，向公众提示深度合成情况：（一）**智能对话、智能写作等模拟自然人进行文本的生成或者编辑服务**；……
3. **《人工智能生成合成内容标识办法》**（2025-09-01 施行）第 2、4、5、8、9、10 条。

#### R4.2 《标识办法》关键条文

> **第二条**：符合《互联网信息服务算法推荐管理规定》《互联网信息服务深度合成管理规定》《生成式人工智能服务管理暂行办法》规定情形的**网络信息服务提供者**（以下简称"服务提供者"）开展人工智能生成合成内容标识活动，适用本办法。

> **第三条**：……**显式标识**是指在生成合成内容或者交互场景界面中添加的，以文字、声音、图形等方式呈现并可以被用户**明显感知**到的标识。**隐式标识**是指采取技术措施在生成合成内容文件数据中添加的，不易被用户明显感知到的标识。

> **第四条**：服务提供者提供的生成合成服务属于《互联网信息服务深度合成管理规定》第十七条第一款情形的，应当按照下列要求对生成合成内容添加显式标识：（一）在**文本的起始、末尾或者中间适当位置添加文字提示或者通用符号提示等标识**，或者在**交互场景界面、文字周边添加显著的提示标识**；……
> 服务提供者提供生成合成内容下载、复制、导出等功能时，应当确保文件中含有满足要求的显式标识。

> **第五条**：服务提供者应当按照《互联网信息服务深度合成管理规定》第十六条的规定，在生成合成内容的**文件元数据**中添加隐式标识……

> **第八条**：服务提供者应当在**用户服务协议**中明确说明生成合成内容标识的方法、样式等规范内容，并提示用户仔细阅读并理解相关的标识管理要求。

> **第九条**：用户申请服务提供者提供没有添加显式标识的生成合成内容的，服务提供者可以在通过用户协议明确用户的标识义务和使用责任后，提供不含显式标识的生成合成内容，并**依法留存提供对象信息等相关日志不少于六个月**。

> **第十条**：用户使用网络信息内容传播服务发布生成合成内容的，应当主动声明并使用服务提供者提供的标识功能进行标识。
> **任何组织和个人不得恶意删除、篡改、伪造、隐匿本办法规定的生成合成内容标识，不得为他人实施上述恶意行为提供工具或者服务**，不得通过不正当标识手段损害他人合法权益。

> **第十四条**：本办法自 **2025 年 9 月 1 日**起施行。

#### R4.3 对"本机私有化、仅回复私聊"的适用性分析

这是本报告技术性最强、也最容易被错误乐观判断的一节。结论：**不能以"本机私有化 + 私聊"为由主张不适用，需要分三步判断。**

**第一步：是否落入前置规章的适用情形（《标识办法》第 2 条的入口）**

- 《生成式 AI 办法》第 2 条第 3 款规定：
  > 行业组织、企业、教育和科研机构、公共文化机构、有关专业机构等研发、应用生成式人工智能技术，**未向境内公众提供**生成式人工智能服务的，**不适用**本办法的规定。
  → 若严格是"企业内部自用、不向公众提供"，可主张不适用。
- **但**：本产品回复的是**商家的外部客户**（不特定的消费者）。这些消费者通过微信私聊触发了 AI 生成内容，他们就是"公众"的一部分。**"1 对 1 私聊"不等于"非公众"**——公众性看的是"服务对象是否为不特定人"，不是"是否群发"。
- 因此，**只要工具被用于对外客服（而非纯内部），就应推定落入适用情形**。

**第二步：是否构成"可能导致公众混淆或误认"（《深度合成规定》第 17 条的触发）**

- 消费者在微信私聊中收到 AI 生成回复，若**无从判断对方是机器人**，即构成"误认"。
- 微信私聊场景下**误认概率极高**：没有界面提示、没有头像标识、语气拟人。
- → 落入第 17 条第 1 款第（一）项"智能对话……模拟自然人"。

**第三步：显式标识如何落地（工程与产品要求）**

《标识办法》第 4 条允许两种方式，任选其一：
- 方式 A：在**文本**的起始/末尾/中间加文字提示（如首条消息"以下回复由 AI 助手生成"或每条末尾加"〔AI 生成〕"）；
- 方式 B：在**交互场景界面**添加显著提示（如软件界面常驻角标、会话窗口顶部提示条、发送前的"AI 生成"标记）。

> **注意**：方式 B 的"界面"必须是**接收方可见**的界面，而不是只在自己电脑上显示。在微信私聊中，唯一能让对方感知的位置就是**消息文本本身**或**对方的微信界面**——后者不可控。因此**实际可行的是方式 A：把标识放进消息文本**。

**第四步：产品红线——不得提供"关闭标识"**

《标识办法》第 10 条第 2 款明确："**不得为他人实施上述恶意行为提供工具或者服务**"。若产品提供"关闭 AI 标识""隐身模式""拟人化模式（隐藏 AI 身份）"选项，该功能本身即可能违法。这是一个**必须从产品中删除**的功能类别。

#### R4.4 执法先例（证明不是纸面义务）

- **2026-04-28**，国家网信办指导属地网信办，对"**剪映**""**猫箱**"App 及"**即梦 AI**"网站因"未有效落实人工智能生成合成内容标识规定要求"等问题，采取**约谈、责令改正、警告、从严处理责任人**等处置处罚措施。这是标识办法落地以来**首次公开点名执法**。
- **2026 年 2 月**专项整治中，全国依法处置超 **1.3 万个**违规账号，清理逾 **54 万条**违法违规信息（据媒体引述监管通报）。
- **微信平台侧**：2025-08-31"微信珊瑚安全"《关于进一步规范人工智能生成合成内容标识的公告》要求用户发布 AI 生成合成内容时主动声明，不得删除/篡改/伪造/隐匿平台标识；2026-03-27《关于持续强化"自媒体"创作者信息来源标注的公告》累计处置 **7418 个**账号。

**结论**：R4 是**有执法先例的红色风险**，且执法对象包括头部企业。对创业团队而言，被约谈/责令改正的概率不低，且一旦被点名，商业信誉损失远大于整改成本。

### R5 数据出境（若调用境外大模型）

#### R5.1 触发条件

若产品调用 OpenAI / Anthropic / Google 等**境外模型 API**，聊天内容（含客户个人信息）将被传输至境外，构成**个人信息出境**。这是本产品最隐蔽的红色风险：技术上只是"调个 API"，法律上是"跨境传输"。

#### R5.2 法条

> **《个人信息保护法》第三十八条**：个人信息处理者因业务等需要，确需向中华人民共和国境外提供个人信息的，应当具备下列条件之一：（一）依照本法第四十条的规定通过国家网信部门组织的**安全评估**；（二）按照国家网信部门的规定经专业机构进行**个人信息保护认证**；（三）按照国家网信部门制定的**标准合同**与境外接收方订立合同，约定双方的权利和义务；（四）法律、行政法规或者国家网信部门规定的其他条件。

> **第三十九条**：个人信息处理者向中华人民共和国境外提供个人信息的，应当向个人告知境外接收方的名称或者姓名、联系方式、处理目的、处理方式、个人信息的种类以及个人向境外接收方行使本法规定权利的方式和程序等事项，并取得个人的**单独同意**。

> **《生成式人工智能服务管理暂行办法》第二十条**：对来源于中华人民共和国境外向境内提供生成式人工智能服务不符合法律、行政法规和本办法规定的，国家网信部门应当通知有关机构采取技术措施和其他必要措施予以处置。

#### R5.3 风险等级与建议

| 情形 | 风险 | 建议 |
|---|---|---|
| 默认调用境外模型，未做任何出境合规 | 🔴 红 | 立即停止，或改为境内已备案模型 |
| 调用境外模型 + 有标准合同/认证 + 单独同意 | 🟠 橙 | 可行但成本高，且模型本身可能未在境内备案 |
| 调用境内已备案模型（DeepSeek/通义/豆包/文心等） | 🟡 黄 | 仍需完成"大模型登记"（见 O3）与 DPA |

> **实务提示**：即使走"境内模型"，也要注意模型的**数据留存与训练条款**。若模型厂商将输入用于训练，等于软件方把客户个人信息"提供"给第三方（个保法 23 条），需要单独同意。签约时必须确认"不用于训练"。

## 3. 橙色风险（高风险，需结构改造）

### O1 腾讯民事追责：不正当竞争与侵权

#### O1.1 判例：聚客通群控软件案

- **案号**：浙江省杭州铁路运输法院 **（2019）浙8601民初1987号**
- **原告**：深圳市腾讯计算机系统有限公司、腾讯科技（深圳）有限公司
- **被告**：浙江搜道网络技术有限公司、杭州聚客通科技有限公司
- **行为**：开发运营"聚客通群控软件"，利用 **Xposed 外挂技术**将"个人号"功能模块嵌套于个人微信运行，实现**自动化、批量化操作**（朋友圈自动点赞、群发消息、被添加自动通过并回复、清理僵尸粉、智能养号），并**监测、抓取**微信账号信息、好友关系链信息、用户操作信息存储于自己服务器。
- **判决**：停止不正当竞争，**共同赔偿 260 万元**及合理费用，消除影响。
- **裁判要点**（对本案极重要）：
  1. 平台对**数据资源整体**与**单一原始数据个体**享有不同数据权益；
  2. 擅自收集微信用户数据、存储于自己控制的服务器，"不仅危及微信用户的数据安全，且对腾讯基于数据资源整体获得的竞争权益构成实质性损害"；
  3. 违反《网络安全法》相关规定，有违商业道德，构成不正当竞争。

> **对本产品的意义**：即使技术手段不同（RPA 而非 Xposed），**"自动化批量操作 + 抓取数据 + 存储于自己服务器"** 这一行为组合与判决认定的损害逻辑高度一致。本产品的 OCR 落库 + 客户管理 + 分析功能，恰好落在"存储于自己控制的服务器（本地数据库）"这一要点上。**这是腾讯起诉本产品最可能援引的判例。**

#### O1.2 法律依据

- **新《反不正当竞争法》**（2025-06-27 修订，**2025-10-15 施行**）新增**第十三条"数据专条"**：明确平台经营者不得以不正当方式获得数据，或使用非法获得的数据进行不正当竞争。
- 同时仍可援引**第二条**（诚信与商业道德原则）作为兜底。
- **《民法典》第一千一百六十九条**（帮助侵权）：教唆、帮助他人实施侵权行为的，应当与行为人承担连带责任。
  → 若用户使用工具实施违约/侵权，软件方"明知"仍提供，可能构成帮助侵权。

#### O1.3 其他民事路径

- **商标侵权**：产品名含"wechat"、宣传中使用微信图标/名称 → 商标侵权 + 不正当竞争（见 O7）。
- **著作权**：规范 1.2.1–1.2.3 涉及软件完整性；RPA 一般不复制代码，风险较低，但 OCR 截图批量保存微信界面可能被主张"复制"。
- **合同关系**：软件方与腾讯之间**没有合同关系**，腾讯只能走侵权/不正当竞争路径；这反而使腾讯更倾向直接起诉（无仲裁条款障碍）。

#### O1.4 风险量级

- 聚客通案判赔 **260 万元**（2019 年判决，违法所得与规模均小于当前市场）。
- 若本产品规模化销售（数百家客户、数万账号），索赔金额可能显著更高。
- 更现实的威慑是：**律师函 → 应用商店/代码托管平台投诉下架 → 客户恐慌性流失**，即使最终胜诉，业务也已中断。

### O2 封号损失的民事责任与免责条款效力

#### O2.1 请求权基础

| 路径 | 依据 | 举证要点 | 现实难度 |
|---|---|---|---|
| 违约 | 合同约定功能/稳定性未达成 | 合同文本、宣传材料、SLA | 若合同已明确"不保证账号安全"，较难成立 |
| 缔约过失 | 隐瞒重大风险、虚假宣传 | 宣传话术、销售记录 | 中 |
| 侵权 | 《民法典》1165 条（过错责任） | 过错、损害、因果关系 | 因果关系举证难（微信不公开封号原因） |
| 消费者保护 | 《消保法》第 20 条（真实信息）、第 55 条（欺诈三倍赔偿） | 面向个人销售时适用 | 若认定欺诈，赔偿放大 |
| 虚假宣传 | 《反不正当竞争法》第 8 条、《广告法》第 28 条 | 宣传"防封""稳定""官方合作" | 行政处罚 + 民事 |

#### O2.2 免责条款效力的三层检验

> **《民法典》第四百九十六条**：格式条款是当事人为了重复使用而预先拟定，并在订立合同时未与对方协商的条款。采用格式条款订立合同的，提供格式条款的一方应当遵循公平原则确定当事人之间的权利和义务，并采取**合理的方式提示对方注意免除或者减轻其责任等与对方有重大利害关系的条款**，按照对方的要求，对该条款予以说明。提供格式条款的一方**未履行提示或者说明义务**，致使对方没有注意或者理解与其有重大利害关系的条款的，对方可以主张该条款**不成为合同的内容**。

> **第四百九十七条**：有下列情形之一的，该格式条款**无效**：（一）具有本法第一编第六章第三节和本法第五百零六条规定的无效情形；（二）提供格式条款一方**不合理地免除或者减轻其责任、加重对方责任、限制对方主要权利**；（三）提供格式条款一方**排除对方主要权利**。

> **第五百零六条**：合同中的下列免责条款**无效**：（一）造成对方**人身损害**的；（二）因**故意或者重大过失**造成对方**财产损失**的。

**逐层结论**：

| 条款写法 | 效力判断 | 理由 |
|---|---|---|
| "因腾讯封号导致的损失，本公司概不负责"（未加粗、未单独确认） | **可能不成为合同内容** | 496 条：未履行提示说明义务 |
| 同上，但加粗 + 单独勾选确认 + 风险告知书 | **B2B 场景下较可能有效** | 商事主体，已充分提示 |
| "本公司不承担任何责任，包括因本公司故意或重大过失造成的损失" | **无效** | 497 条 + 506 条第（二）项 |
| "赔偿上限为乙方已支付的服务费" | **通常有效**（B2B） | 商事主体可约定责任上限；但不覆盖故意/重大过失与人身损害 |
| 面向个人消费者使用上述条款 | **效力显著降低** | 《消保法》第 26 条：不得排除或限制消费者权利 |

#### O2.3 一个被忽视的反向风险

本产品 README 已写"这类自动化不能保证账号不受限制或封禁"。这句话：
- **对用户告知有利**（证明已提示风险，降低欺诈认定）；
- **但在刑事/行政认定中是不利证据**——它证明软件方**明知**产品会导致封号仍商业化销售。在"明知他人实施……违法犯罪行为而为其提供程序、工具"的认定中，"明知"是主观要件。
- **建议**：将该表述升级为**独立的风险告知书 + 客户书面确认**，并把"明知"转化为"已充分披露、客户自主决策"，而不是仅留一句 README 免责。

### O3 生成式 AI 备案 / 登记 + 算法备案

#### O3.1 三轨制

根据监管实践（2026 年律师实务文章与地方网信办口径），生成式 AI 相关程序义务分为三条轨道：

| 轨道 | 适用对象 | 周期（实务） | 本产品是否触发 |
|---|---|---|---|
| **算法备案** | 算法服务提供者（几乎所有 AI 服务） | 2–4 个月 | SaaS 形态：**触发**；纯本地自用：可主张不触发 |
| **大模型登记** | 调用**已备案**模型 API、不改输出的服务方 | 1–3 个月 | SaaS / B2B2C：**触发** |
| **大模型备案** | 自研 / 微调模型的服务方 | 6–8 个月 | 若基于客户数据微调：**触发** |

#### O3.2 法条依据

> **《生成式 AI 办法》第十七条**：提供具有**舆论属性或者社会动员能力**的生成式人工智能服务的，应当按照国家有关规定开展**安全评估**，并按照《互联网信息服务算法推荐管理规定》履行**算法备案**和变更、注销备案手续。

> **《深度合成规定》第十九条**：具有舆论属性或者社会动员能力的深度合成服务提供者，应当按照《互联网信息服务算法推荐管理规定》履行备案和变更、注销备案手续。**深度合成服务技术支持者应当参照前款规定履行备案**和变更、注销备案手续。完成备案的深度合成服务提供者和技术支持者应当在其对外提供服务的网站、应用程序等的显著位置标明其备案编号并提供公示信息链接。

> **《生成式 AI 办法》第二十二条**：（二）生成式人工智能服务提供者，是指利用生成式人工智能技术提供生成式人工智能服务（**包括通过提供可编程接口等方式提供**生成式人工智能服务）的组织、个人。

**关键点**：《深度合成规定》第 19 条第 2 款把"**技术支持者**"也纳入备案。软件方提供"AI 回复能力"给商家使用，可能被认定为技术支持者——**这意味着即使只卖工具，也可能有备案义务**。

#### O3.3 触发判断

| 形态 | 是否"向境内公众提供" | 备案/登记判断 | 等级 |
|---|---|---|---|
| 严格企业内部自用（员工内部，不对客户） | 否 | 可主张不适用（《生成式 AI 办法》第 2 条第 3 款） | 🟡 |
| 本地单机，但用于回复**商家外部客户** | **是**（对象为不特定消费者） | 应做**大模型登记**（调已备案模型）+ 算法备案；商家为服务提供者，软件方可能为技术支持者 | 🟠 |
| SaaS 多租户，面向商家销售 | **是** | **大模型登记 + 算法备案**；若微调 → 大模型备案 | 🟠 |
| 自研/微调模型 | 是 | 大模型备案（6–8 个月） | 🔴（周期与成本） |

#### O3.4 执法态势（2026 年显著收紧）

- **2026-04** 中央网信办部署"**清朗·整治 AI 应用乱象**"专项行动，将"**未按规定履行大模型备案登记义务**"列为**第一阶段重点整治内容**，把"应备未备""应登未登"作为重点。
- 地方网信办已出现案例：企业调用已备案模型 API 集成 AI 问答，被认定"属于面向公众提供生成式 AI 服务的应用"，需履行备案/登记并整改。
- 截至 **2026-06-30**，全国已有 **988 款**生成式 AI 服务完成备案、**598 款**完成登记（据律师实务文章引述监管数据，**未在网信办官网逐条核实**）。

#### O3.5 罚则

- 《生成式 AI 办法》第 21 条：依《网络安全法》《数据安全法》《个人信息保护法》处罚；无规定的，警告、通报批评、责令限期改正；拒不改正或情节严重，责令暂停提供相关服务。
- 《算法推荐规定》对未履行备案义务设定了警告、责令限期改正及罚款。
- 《标识办法》第 13 条：由网信、电信、公安、广电等部门依职责按有关法律处理（实际执法如剪映案：约谈、责令改正、警告、从严处理责任人）。

### O4 增值电信业务许可（ICP / EDI）

#### O4.1 判断逻辑

| 业务形态 | 是否需要许可 | 依据 |
|---|---|---|
| 纯本地软件授权（一次性买断，无线上服务） | 一般**不需要** ICP/EDI | 不构成"通过互联网向用户提供信息服务" |
| SaaS 订阅（云端部署、账号登录、在线使用） | **需要 ICP 备案**；收费则可能构成**经营性**，需 **ICP 许可证** | 《互联网信息服务管理办法》 |
| SaaS 含多租户、订单、支付、数据处理 | 可能还需 **EDI 许可证**（在线数据处理与交易处理业务） | 《电信业务分类目录》B21 |
| 仅提供软件下载 + 本地运行 + 无云端账号体系 | 一般不需要 | — |

#### O4.2 实务提示

- 增值电信业务许可由**省级通信管理局**审批，要求：公司注册资本 100 万元以上、社保人员在册、域名归属、服务器在境内、经营范围含"增值电信业务"等。
- 无证经营的后果：责令改正、罚款、责令停业整顿；情节严重的可能触及**非法经营**的讨论（实践中以行政处罚为主）。
- **注意**：即使只做"软件授权"，若附带云端账号、激活服务器、远程配置、数据同步，也可能被认定为提供在线服务。

### O6 帮助信息网络犯罪活动罪与反电信网络诈骗法

#### O6.1 触发场景

- 客户将自动回复/批量加好友用于**电诈引流、杀猪盘、赌博推广、虚假投资**；
- 软件方提供**话术模板、批量加好友、群发、规避封号**能力，且"明知或应知"；
- 软件方按"账号数/发送量"收费，商业模式与违法使用强相关。

#### O6.2 法条

> **《刑法》第二百八十七条之二**（帮助信息网络犯罪活动罪）：明知他人利用信息网络实施犯罪，为其犯罪提供互联网接入、服务器托管、网络存储、通讯传输等技术支持，或者提供广告推广、支付结算等帮助，情节严重的，处三年以下有期徒刑或者拘役，并处或者单处罚金。

> **《反电信网络诈骗法》第十四条**：任何单位和个人不得非法制造、买卖、提供或者使用下列设备、软件：（一）电话卡批量插入设备；（二）具有改变主叫号码、虚拟拨号、互联网电话违规接入公用电信网络等功能的设备、软件；（三）**批量账号、网络地址自动切换系统，批量接收提供短信验证、语音验证的平台**；（四）其他用于实施电信网络诈骗等违法犯罪的设备、软件。

> **《反电信网络诈骗法》第三十八条**（罚则）：组织、策划、实施、参与电信网络诈骗活动或者为电信网络诈骗活动提供帮助，构成犯罪的，依法追究刑事责任。

#### O6.3 对本产品的意义

- 单账号、白名单、客服场景 → 帮信罪风险低；
- **多账号、批量加好友、群发、虚拟定位、账号切换** → 直接对应第 14 条第（三）项的外观，风险显著上升；
- 建议在产品中**永久移除**多开、批量加好友、虚拟定位、账号切换功能，并在用户协议中明确禁止用于诈骗/赌博，保留封禁权与举报义务。

### O8 SaaS 形态的责任放大（详见 §7）

SaaS 不是"把软件放到云上"这么简单，它同时改变四个身份：
1. 从"软件提供者"变为**个人信息处理者/受托处理者**；

同时，腾讯的起诉对象会从"难以触达的终端用户"变为"**可触达、有赔偿能力的服务商**"。这是风险量级跃迁的根本原因。

## 4. 黄色风险（可管理）

### Y1 宣传合规

- 禁用词："防封""不封号""稳定不封""官方合作""微信认证""破解""免检测""养号"。
- 依据：《反不正当竞争法》第 8 条（虚假宣传）、《广告法》第 28 条（虚假广告）、《消保法》第 20 条（真实信息）。
- 后果：行政处罚（广告费用 3–5 倍或 20 万–100 万元）、民事三倍赔偿、平台投诉下架。

### Y2 消费者权益与 AI 误导

- AI 自动回复若作出**价格、库存、效果、承诺性表述**（"保证治好""最低价""三天到货"），可能构成：
  - 虚假宣传（反法 8 条）；
  - 欺诈 → **退一赔三**（消保法 55 条）；
  - 若涉及医疗、药品、金融、教育等特殊行业，另有专门法规。
- **建议**：AI 回复设置"**不得作出承诺性表述**"的系统提示与后置校验；高风险行业（医疗、金融、法律、教育）默认禁用自动回复或强制人工复核。

### Y3 分发渠道

- GitHub / 代码托管平台：腾讯可发**律师函/DMCA** 要求下架；README 已注明仓库为私有，但若公开分发二进制，风险上升。
- 应用商店（含 Mac App Store）：审核会因"自动化操控其他 App""使用辅助功能"被拒（Apple 审核指南对自动化其他应用有限制）。
- Agent 插件市场（Claude Code / Codex / Cursor 等）：平台可能因合规风险下架。

### Y4 合同治理缺失

商业化前必须具备：
- 《软件许可协议》/《SaaS 服务协议》；
- 《数据处理协议（DPA）》——受托处理目的、期限、方式、种类、安全措施、审计、删除返还；
- 《风险告知书》——明确平台规则风险、封号可能、不承诺账号安全；
- 《AI 使用规范》——禁止用途、标识要求、内容责任；
- 《SLA》——可用性、支持响应、免责范围、责任上限；
- 《退出与数据删除条款》——终止后删除/返还数据及证明。

### Y5 敏感信息与未成年人

- 医疗健康、金融账户、行踪轨迹、特定身份、不满 14 周岁未成年人信息 → 敏感个人信息。
- 触发：单独同意 + 特定目的 + 充分必要性 + 严格保护措施 + PIA。
- 建议：**默认不处理**敏感信息（内容过滤 + 拒答 + 脱敏），并在合同中排除相关行业客户。

## 5. 五个必答问题的详细回答

### Q1：只操作自己账号、只回复白名单客户，是否仍违反微信个人账号使用规范？处罚形态与概率？

**结论：仍然违反，且是确定性违规。**

**理由（四层）**：

1. **规范文本层面**：1.2.6 禁止的是"通过非腾讯授权的第三方软件……**进行自动化操作**，对微信软件及其组件、模块、**界面**、数据等进行访问、读取或控制"。该条：
   - 不区分账号归属（自己的账号同样适用）；
   - 不区分操作对象（白名单客户同样是"使用微信软件及服务"）；
   - 明确包含"**界面**"（封死"只读 UI 不碰内存"的抗辩）；
   - 同时禁止"**制作、发布、传播上述工具**"（卖工具本身违规）。

2. **协议文本层面**：《腾讯微信软件许可及服务协议》8.2.1.6 与上述条款同文；更关键的是 **2.3.1 将使用许可限定为"非商业目的"**——**把本软件用于商业经营（收费客服、代运营）本身即构成违约**，与是否改动功能无关。

3. **平台公告层面**：2026-01-29 公告把"截图/辅助服务读取"与"模拟按键、自动化脚本实现自动回复"逐项列为治理对象；2024-03-26 公告已把"微信机器人……自动回复、自动聊天"列为外挂类型。**白名单不是豁免事由，因为平台检测的是行为特征而非对象范围。**

4. **平台检测能力层面**：规范 3.4 条保留了对"异常大量信息""高频异常行为"的独立判断权；公告明确"通过技术模型与用户举报相结合"。RPA 的行为特征（固定间隔、毫秒响应、无输入法轨迹、7×24 在线、剪贴板写入）具有较强可识别性。

**处罚形态**（阶梯）：
警告 → 限制部分功能 → 限制登录（短期，需辅助解封）→ 长期限制 → 永久封号/回收账号 → 关联账号连带处置 → 公告处理结果。

**概率估计**（专家判断，非官方统计）：
- 低频白名单（<30 条/日）+ 主号实名/支付/正常社交：12 个月内被限制/警告 **30%–50%**，永久封号 **5%–10%**；
- 中频（30–150 条/日）+ 自动通过好友：限制/封禁 **60%–80%**，永久 **20%–30%**；
- 高频（>200 条/日）+ 多开/批量：封禁 **>90%**，二次违规通常永久。

> **商业含义**：即使按最乐观的低频场景，也有约三分之一到一半的客户会在一年内遭遇至少一次封号/限制。这意味着**"卖工具 + 客户自担风险"的商业模式，客户留存率与口碑会被封号事件持续侵蚀**；而"承诺不封号"又会把责任揽回自己身上。这是该赛道商业化的结构性矛盾。

### Q2：卖"工具/软件授权"与卖"SaaS 托管代运营"的法律责任差异？

#### Q2.1 责任矩阵

| 维度 | 工具/软件授权 | SaaS 托管代运营 |
|---|---|---|
| **平台规则违规主体** | 用户（使用方）违规；软件方另因"制作、发布、传播工具"违规 | 服务方直接违规（既提供工具又实施操作） |
| **腾讯民事追责对象** | 用户为主，软件方可被列共同被告（帮助侵权/不正当竞争） | **服务方为首要被告**（可触达、有赔偿能力） |
| **个人信息处理者身份** | 若本地存储 → 软件方仍可能是处理者；若纯工具不接触数据 → 用户为处理者 | **服务方是受托处理者或独立处理者**，全套个保义务 |
| **网络运营者义务**（等保/日志/违法信息处置） | 一般不适用（除非提供云服务） | **全部适用** |
| **生成式 AI 备案/登记** | 可主张"技术支持者"参照备案；纯本地可主张不适用 | **明确触发**（服务提供者） |
| **增值电信许可（ICP/EDI）** | 一次性授权通常不需要 | **需要**（经营性互联网信息服务/在线数据处理） |
| **AI 内容标识义务** | 软件方提供"标识能力"；用户负责标识 | **服务方直接承担标识义务** |
| **封号损失的合同责任** | 用户自担为主；软件方可通过免责条款限缩（有效性见 O2） | 服务方**直接违约**（承诺了代运营效果） |
| **刑事风险** | 提供工具型（285 条 3 款）；风险中等 | 既提供又实施，且通常规模更大；**风险更高**，且更易被认定为"明知" |
| **数据出境** | 取决于用户配置 | 服务方统一配置，**责任集中** |
| **责任量级（专家判断）** | 基准 1× | **3–5×** |

#### Q2.2 关键差异的底层逻辑

1. **"距离数据越近，责任越重"**：SaaS 方直接持有全部客户的聊天记录 → 一旦泄露，是"大量数据泄露"，触发个保法 66 条"情节严重"档（5000 万或 5% 营业额）的概率大幅上升。
2. **"距离行为越近，越像共同实施"**：SaaS 代运营是服务方自己的服务器在跑自动化 → 腾讯起诉时无需证明"帮助"，可直接主张"实施"。
3. **"收费模式暴露主观状态"**：按账号数/发送量收费，会被用来证明"以违规为业"；工具买断制相对中性。
4. **"可触达性决定被诉概率"**：终端用户分散、单笔金额小，腾讯起诉成本高；SaaS 服务商集中、有对公账户、有品牌，是理想的被告。

#### Q2.3 一个反直觉的结论

**工具形态并不"安全"，只是"责任分散"。** 因为规范 1.2.6 明确禁止"制作、发布、传播上述工具"，软件方本身就在违规链条上；且刑法 285 条 3 款惩罚的是"**提供**"行为，工具形态恰好是"提供"的典型。**因此不能得出"卖工具就没事"的结论。**

### Q3：《AI 生成合成内容标识办法》对"本机私有化、仅回复私聊"是否适用？备案是否触发？

#### Q3.1 标识义务：适用（红色）

**判断链**：

```
是否落入《生成式AI办法》/《深度合成规定》/《算法推荐规定》情形？
  → 生成式AI办法第2条：是否"向境内公众提供"？
      → 服务对象是商家的外部客户（不特定消费者）→ 是
  → 深度合成规定第17条第1款第（一）项：智能对话模拟自然人，可能导致混淆/误认？
      → 微信私聊无任何 AI 提示 → 是
→ 落入《标识办法》第2条 → 适用
→ 第4条：加显式标识（文本或交互界面）
→ 第5条：加隐式标识（文件元数据；纯文本消息场景适用性弱，但不是免责理由）
→ 第8条：用户协议说明标识方法
→ 第10条：不得删除/篡改/隐匿；不得为他人提供删除工具
```

**"本机私有化"为什么不构成豁免**：
- 《标识办法》第 2 条看的是"是否为网络信息服务提供者 + 是否落入前三部规章情形"，不看"部署在哪里"。
- 只要 AI 生成内容**通过网络（微信）传递给他人**，就具有"网络信息服务"属性；"私有化"只是部署方式。
- 唯一可主张豁免的路径是《生成式 AI 办法》第 2 条第 3 款"**未向境内公众提供**"——但回复外部客户就是向公众提供。

**"仅回复私聊"为什么不构成豁免**：
- "私聊"是传播范围，不是"公众性"的判断标准。公众性 = 服务对象是否**不特定**。
- 商家的客户群体是不特定的（任何加好友的人），且会持续新增。
- 私聊恰恰是"误认"最容易发生的场景——没有群聊的多人见证，没有界面提示，只有一个"像人"的对话者。

**落地建议**：
1. 每条 AI 生成消息末尾加显式标识（如 `〔AI 生成〕`），或首条消息声明 + 会话内定期提示；
2. 在软件界面显示"AI 辅助回复中"状态；
3. 用户协议中说明标识方法（第 8 条）；
4. **删除任何"关闭标识/隐身/拟人化"选项**（第 10 条）；
5. 若客户要求"不带标识"，需按第 9 条处理：通过用户协议明确用户的标识义务和使用责任，并**留存日志不少于 6 个月**——但这条对"面向消费者"的场景并不实用，且不能免除用户自身的标识义务。

#### Q3.2 备案/登记：本地自用可主张不触发；SaaS/B2B2C 触发（橙色）

| 场景 | 判断 | 依据 |
|---|---|---|
| 纯本地、商家自己用、不对外提供 AI 服务（仅辅助自己回复） | 可主张不适用（第 2 条第 3 款） | 但"回复外部客户"使该主张变弱 |
| 本地工具，但用于回复商家客户 | 商家可能构成服务提供者 → 需登记/备案；软件方可能构成技术支持者 → 参照备案 | 深度合成规定 19 条第 2 款 |
| SaaS 多租户 | 明确触发：大模型登记（调已备案模型）+ 算法备案 | 生成式AI办法 17 条；深度合成规定 19 条 |
| 自研/微调 | 大模型备案（6–8 个月） | 实务口径 |

**关键提醒**：
- "调用已备案模型 API 就不用管"是**常见误区**。监管口径是：调用已备案模型的**应用/功能**，由地方网信办开展**登记**；若对输出做了实质性二次处理（内容过滤、重组、安全审核、格式优化），可能被要求从"登记"升级为"备案"。
- 2026 年"清朗·整治 AI 应用乱象"专项行动把"应备未备、应登未登"列为重点，**这是当前最活跃的执法方向之一**。

### Q4：存储客户聊天记录/图片（含他人个人信息）需要什么合法性基础？

#### Q4.1 最低合规要求（缺一即红色）

| # | 要求 | 依据 | 落地物 |
|---|---|---|---|
| 1 | 告知处理者身份、目的、方式、种类、保存期限、权利行使方式 | 个保法 17 条 | 隐私政策 + 首次对话告知 |
| 2 | 取得同意或其他合法性基础 | 13 条 | 同意记录（可追溯） |
| 3 | 敏感信息单独同意 + 特定目的 + 充分必要 + 严格保护 | 28/29/30 条 | 分级 + 单独同意弹窗 |
| 4 | 委托处理协议 + 监督 | 21 条 | DPA |
| 5 | 向第三方提供需告知 + 单独同意 | 23 条 | 模型厂商名单披露 |
| 6 | PIA + 记录保存 3 年 | 55/56 条 | PIA 报告 |
| 7 | 最短必要 + 保存期限 | 6/19 条 | 数据保留策略 + 自动删除 |
| 8 | 安全措施（加密、权限、审计、去标识化） | 51 条 | 技术方案 |
| 9 | 境内存储；出境需 38/39 条 | 38/39 条 | 境内模型/云 |
| 10 | 个人权利响应（查阅、复制、更正、删除、可携带） | 44–50 条 | 工单流程 |

#### Q4.2 三条容易走错的路径

**错误路径 1："商家同意了就行"**
- 商家是个人信息处理者，但它对**其客户**的告知同意义务**不能通过"同意使用软件"来履行**。
- 必须由商家向其客户告知（加好友欢迎语、服务须知、隐私政策），或由软件在首次对话时以商家名义告知。
- 若商家未做，软件方作为受托处理者虽不直接对消费者负责，但会被认定为"未监督受托处理活动"（21 条），且平台规则 4.1 条同时违规。

**错误路径 2："聊天记录不是敏感信息，随便存"**
- 见 R3.3：整体不敏感 ≠ 内容不含敏感。图片风险更高。
- 一旦含医疗/金融/行踪/14 岁以下未成年人信息，即触发单独同意 + 严格保护。

**错误路径 3："本地存储不涉及个人信息保护法"**
- 个保法适用看"是否处理个人信息"，不看"存在哪里"。本地 SQLite 同样是"处理"。
- 本地存储反而增加泄露风险（无集中安全管控、无审计、设备丢失即泄露）。

#### Q4.3 建议的数据架构

```
采集层：仅 OCR 必要字段（会话文本、时间、发送方），不存全屏截图
  ↓
存储层：加密（至少 SQLCipher / 文件级加密）；分表分账号；TTL 自动删除
  ↓
使用层：默认不用于训练；如需分析，先脱敏（去手机号/微信号/地址）
  ↓
出境层：默认境内；禁止默认调用境外模型
  ↓
治理层：PIA + DPA + 权限矩阵 + 审计日志 + 删除证明
```

### Q5：客户因使用该工具被封号，软件方的民事责任与免责条款有效性？

#### Q5.1 责任路径与成立条件

| 路径 | 成立条件 | 抗辩 | 结果量级 |
|---|---|---|---|
| **违约** | 合同约定"保证账号安全/稳定运行"，或未达约定功能 | 合同已明确风险、用户已知悉 | 退费 + 直接损失 |
| **缔约过失** | 隐瞒重大风险、虚假宣传 | 已充分披露 | 信赖利益赔偿 |
| **侵权**（民法典 1165） | 过错 + 损害 + 因果关系 | 封号主因是平台规则而非工具瑕疵；因果关系举证难 | 实际损失 |
| **消费者欺诈**（消保法 55） | 虚假宣传"防封"等 | 无虚假表述 | 退一赔三 |
| **帮助侵权**（民法典 1169，腾讯主张） | 明知用户违约仍提供工具 | 已提示、已限制 | 连带责任 |

#### Q5.2 免责条款：能否"封号概不负责"？

**结论：可以写，但效力有限，且写法决定成败。**

三层检验（见 O2.2）：
1. **496 条（提示说明）**：格式条款必须"采取合理方式提示"并"按对方要求说明"。未做到 → 对方可主张**不成为合同内容**。
2. **497 条（内容控制）**：不合理免除自身责任、加重对方责任、限制对方主要权利 → **无效**。
3. **506 条（绝对无效）**：**故意或重大过失造成对方财产损失的免责条款无效**。

**实务判断**：

| 场景 | 免责条款效力 |
|---|---|
| B2B（商家客户），条款加粗 + 单独确认 + 风险告知书 | **较可能有效**（商事主体，意思自治空间大） |
| B2B，但条款藏在附件/未提示 | **可能不成为合同内容** |
| B2C（个人用户），任何形式 | **效力显著降低**（消保法 26 条） |
| 软件方**明知**产品必然导致封号仍宣称"安全" | **可能被认定为故意/重大过失 → 免责无效** |
| 约定"责任上限 = 已付服务费" | **通常有效**（B2B），但不覆盖故意/重大过失 |

#### Q5.3 一个更现实的风险：举证责任与群体性事件

- 微信**不公开封号具体原因**（仅提示"使用外挂/非官方客户端"），客户难以证明"是工具导致"；
- 但反过来，软件方也难以证明"不是工具导致"；
- 若**同一批次大量客户同时被封**，法院可能推定因果关系存在；
- 群体性事件（几十家客户同时被封）会引发集体投诉、媒体曝光、平台投诉下架，商业损失远超单个赔偿。

#### Q5.4 建议的合同结构

1. **风险告知书**（独立文件，客户签字/勾选）：
   - 明确"本产品使用第三方自动化技术，违反平台规则，存在账号被限制或封禁的风险"；
   - 明确"不承诺账号安全、不承诺不被检测"；
   - 明确"客户应自行评估并承担账号风险"。
2. **责任限制条款**：
   - 赔偿上限 = 客户已支付的服务费；
   - 排除间接损失、可得利益损失、客户资源损失；
   - **不排除**故意/重大过失（否则整条可能无效）。
3. **不承诺条款**：禁止销售人员在口头/书面作出"防封""稳定"承诺；合同中加入"完整协议条款"（排除口头承诺）。
4. **终止与救济**：客户可因封号终止并获按比例退费（把无限赔偿转化为有限退费，反而更可控）。
5. **保险**：探索网络安全责任险/职业责任险，但注意**违规业务通常不在承保范围**（需提前与保险人确认）。

## 6. 企业微信作为合规替代路径的边界

### 6.1 能力边界

| 能力 | 企业微信是否支持 | 说明 |
|---|---|---|
| 与微信用户 1:1 沟通 | ✅ 通过"客户联系"添加为外部联系人（需用户同意） | 不是"个人微信好友"，是"外部联系人" |
| 微信用户主动咨询 | ✅ 通过"微信客服"（WeCom KF） | 需企业认证 + 配置 |
| 消息自动回复 | ✅ 通过官方 API（客服消息/应用消息） | 受频率、内容、用户主动触发限制 |
| 会话内容存档 | ✅ 需付费开通 + 双告知 | 见 6.2/6.3 |
| 批量加好友 | ❌ 官方不提供，且违反规则 | 不得使用任何"批量"能力 |
| 操控个人微信 | ❌ 明确禁止 | 企业微信不能自动化个人微信客户端 |
| 群发营销 | ⚠️ 受限（客户群发有次数/对象限制） | 需符合"用户同意 + 不骚扰" |

### 6.2 成本结构（据开发者社区与服务商公开口径，**以官方最新报价为准**）

| 项目 | 参考价格 | 备注 |
|---|---|---|
| 企业微信认证 | 300 元/年（审核服务费） | 未认证功能与规模受限 |
| 会话内容存档 | **900 元/人/年**（服务版）、**1800 元/人/年**（企业版） | 按开通账号数计费；企业版含语音通话等 |
| 接口许可（基础账号/互通账号） | 按**客户企业维度**累进阶梯计费，基础/互通两类 | 服务商调用接口需购买；2022-05-16 起取代原"技术服务费" |

> **成本含义**：一个 50 人客服团队，仅会话存档一项即 4.5 万–9 万元/年；再加接口许可与认证。这与"卖 999 元软件授权"是完全不同的商业模型。

### 6.3 合规约束（不是"开了就合规"）

1. **企业认证 + 超级管理员**才能申请会话存档；
2. **双告知**：员工端需同意（客户端提示），外部客户需收到"服务须知"；**客户不同意 → 限制收发消息或被移出群**；
3. **数据必须存储在中华人民共和国境内**；
4. **私钥由企业自管**，平台不解密；私钥丢失 → 历史存档不可恢复；
5. **用途限制**：仅限合规审计、客诉举证、风控、服务质量；不得用于与工作无关用途、不得外泄或出售；
6. **最小必要 + 分级授权 + 审计留痕**；
7. **不得屏蔽平台提示**（屏蔽即违规）；
8. 企业微信同样禁止外挂/非官方工具；服务商需通过审核。

### 6.4 结论：企业微信能覆盖什么、不能覆盖什么

**能覆盖**：
- 合规的 1:1 客户沟通与自动回复（官方 API）；
- 合规的会话存档（付费 + 双告知）；
- 客户资产归属于企业（离职继承）；
- 与微信用户的连接（外部联系人、微信客服）。

**不能覆盖**：
- **存量个人微信好友的自动化**——这是本产品当前的核心卖点，也是企业微信路径**无法迁移**的部分；
- 高频/批量主动触达；
- "零成本"——按账号/年付费，成本结构完全不同；
- "无感迁移"——客户需要重新加好友、重新建流程。

> **战略含义**：企业微信是**唯一可规模化商业化的合规路径**，但它要求产品**改变形态**（从"操控个人微信"变为"接入官方 API 的客服中台"），并接受**按人头付费的成本结构**。如果目标客户的核心诉求是"把个人微信里几千个好友自动化"，那么企业微信路径**解决不了这个问题**——这正是该赛道商业化的根本困境。

## 7. 两种商业形态的责任对比（汇总）

| 维度 | 工具/软件授权 | SaaS 托管代运营 |
|---|---|---|
| 典型定价 | 买断 999–9,999 元 | 订阅 500–5,000 元/月/账号 |
| 客户画像 | 个体商家、小团队 | 中大型商家、代运营公司 |
| 平台违规主体 | 用户 | 服务方 |
| 腾讯起诉对象 | 用户（软件方可能共同被告） | **服务方** |
| 个人信息处理者 | 视是否接触数据 | **服务方（受托/独立）** |
| 等保/日志/违法信息处置 | 一般不适用 | **全部适用** |
| 生成式 AI 备案/登记 | 技术支持者参照备案 | **明确触发** |
| ICP/EDI | 通常不需要 | **需要** |
| 数据出境责任 | 用户配置 | **服务方集中承担** |
| 封号损失责任 | 可通过免责条款限缩 | 直接违约，难限缩 |
| 刑事风险 | 285 条 3 款（提供工具） | 285 条 3 款 + 可能共同实施 + 帮信 |
| 责任量级（专家判断） | 1× | **3–5×** |
| 商业上限 | 低（一次性收入、客户流失快） | 高（复购、规模化） |
| 合规可行性 | 仍违反平台规则 | 需全面重构 |

**结论**：这是一个"**风险与收益同向放大**"的赛道。工具形态风险较低但商业上限低且仍违规；SaaS 形态商业上限高但法律责任成倍放大，且需要一整套资质、备案、数据合规基础设施。**两者都不是"合规"的，区别只是"违规的哪一层"。**

### 8.4 推荐的商业化形态（按可行性排序）

| 排序 | 形态 | 合规性 | 商业上限 | 说明 |
|---|---|---|---|---|
| ① | **企业微信/微信客服官方 API 的客服中台**（含 AI 辅助、会话存档、CRM） | 可合规 | 高 | 需资质、备案、按人头成本；放弃"个人微信存量好友"场景 |
| ② | **纯本地、单机、不销售、仅自用的效率工具**（开源或内部使用） | 低风险（仍违反平台规则但无商业化责任） | 无 | 不作为生意 |
| ③ | **个人微信 RPA 工具授权**（不承诺防封、强风险告知、责任上限） | 违规（平台层面），民事可控 | 低 | 客户流失快、口碑差、腾讯可起诉 |
| ④ | **SaaS 托管代运营** | 违规 + 多重资质缺失 | 名义高、实际不可持续 | 法律责任最重，不建议 |

> **推荐**：若必须商业化，走 ①；若只是想把现有能力变现，走 ③ 但把预期降到"小众工具"；**不要走 ④**。

## 11. 给决策层的三句话

1. **红线不在"回复谁"，在"用什么方式回复"**——微信 2026-01-29 公告已经把本产品的技术栈逐项写进了违规清单，"自有账号 + 白名单"不构成任何抗辩。
2. **刑事风险是功能清单的函数，不是行业属性**——纯 UI 自动化风险低，但每增加一个"绕过限制"的功能（多开、免扫码、虚拟定位、批量加好友、规避检测），就向 285 条 3 款移动一格；这条线必须由产品设计主动守住。
3. **唯一可规模化的合规路径是企业微信官方 API，但它要求放弃"个人微信存量好友自动化"这个核心卖点**——如果这个卖点不能放弃，那么这门生意的本质是"高封号率 + 高法律风险 + 低商业上限"的小众工具生意，应据此重新设定估值与预期。
